# Hook Outputs and Main Push Guard Task

## Objective

Deliver valid hook outputs to the model, align the Codex hook bindings, and
close the routes to a direct push to `main`, as SPEC-0238 states.

## Inputs and Authorization

- **Request:** the owner asked on 2026-10-13 to review and then fix and
  extend the PreCompact hook, the Codex hooks and direct pushes to `main`
  ("점검후 수정하고 보완").
- **Baseline:** `main` `f1214c839`.
- **Reviews used as input:** an independent `security-auditor` review of
  `.claude/settings.json` and the hooks, a `rules-engineer` review of
  `.agents`, `.claude` and `.codex`, and a documentation check of Claude Code
  permissions, settings and hooks, all on 2026-10-13.
- **Not done here:** remote GitHub protection, installing the local git hook,
  and user-global provider settings.

## Work Log

### Owner Decisions

On 2026-10-13, through AskUserQuestion (multi-select), the owner chose two
`.claude/settings.json` permission changes for this Spec: "Remove grep/rg
allows" and "Deny reads of secrets". Not chosen, and so left unchanged: more
destructive-command deny rules (`rm -fr`, `rm -r -f`, `docker compose -f x
down`, `sudo`, `docker rm`, `docker volume prune`), and removing project
`autoMode` and `"$defaults"` from `permissions.allow`, which the documentation
says have no effect in project settings. Those stay open findings the owner
declined for now.

### W1 Hook Outputs

Documentation read on 2026-10-13: Claude Code accepts only top-level
`decision`/`reason` or exit 2 for PreCompact and no `hookSpecificOutput`;
SessionStart takes `hookSpecificOutput.additionalContext` with the matchers
`startup`, `resume`, `clear` and `compact`; PreToolUse takes
`additionalContext`; `systemMessage` is shown to the user only
(<https://code.claude.com/docs/en/hooks>). Codex accepts `systemMessage` and
`additionalContext` on SessionStart and PreToolUse and only common fields on
PreCompact (<https://learn.chatgpt.com/docs/hooks>). One output therefore
serves both providers.

- PreCompact now prints its state snapshot as `systemMessage` only.
- SessionStart reads the payload `source`, prints its context as
  `hookSpecificOutput.additionalContext`, names root `AGENTS.md` or `CLAUDE.md`
  and the bootstrap policy, and adds a re-read-the-Task reminder when the
  source is `compact`. Both providers register SessionStart with matcher `*`,
  so per their documentation it runs after compaction; for Codex that is not
  observed.
- PreToolUse sends its edit guidance and hookify warnings as
  `additionalContext` instead of `systemMessage`.
- The seven `.claude/hooks/*.sh` wrappers said they were generated by the
  provider renderer, which renders no hook; their headers now say they are
  authored thin wrappers.

### W2 Codex Hooks

  `Bash|apply_patch` and PostToolUse `apply_patch`, the names Codex emits

### W3 Direct Push to Main

- The `block-direct-main-push` rule (1.1.0) matches an explicit `main`
  destination in every form: `main`, `HEAD:main`, `HEAD:refs/heads/main`,
  `+main`, `x:main`, `-u`, `--force`, `git -C <dir>`, and compound commands.
- `hook_rules.implicit_main_push` judges a push whose refspec is implicit
  (`git push`, `git push origin`) by the branch and `@{push}` target of the
  directory it runs in, following `cd` and `git -C`, and treats `--all` and
  `--mirror` as pushes to `main`. The dispatcher denies those too.
- `scripts/hooks/pre-push-guard.sh` refuses any push whose remote ref is
  `refs/heads/main`, reading both the pre-commit environment and raw pre-push
  stdin. `.pre-commit-config.yaml` installs `pre-push` by default and runs only
  this guard at that stage (`default_stages: [pre-commit, manual]`). The
  workflow-contract test that forbade any local pre-commit hook now allows
  exactly this push-time guard.
- An agent ran `pre-commit run block-main-push --hook-stage pre-push` during
  this work. `quality-standards.md` prohibits a direct agent `pre-commit run`
  and no authorization covered it, so that run is a process violation and is
  not evidence here. The guard is evidenced by the direct-script and
  configuration tests; wiring at the installed pre-push stage stays an owner
  observation after `pre-commit install --hook-type pre-push`.
- `.github/rulesets/main-protection.md` records the two direct pushes of
  2026-10-13 and that the last read-back reported `enforce_admins=false`.

### W4 Claude Permissions

- Removed `Bash(grep:*)` and `Bash(rg:*)` from `permissions.allow`; the
  built-in Grep tool stays. No test or script relied on them.
- Added to `permissions.deny`: `Read(./secrets/**)`, `Read(./.env)`,
  `Read(./**/.env)`, `Read(~/.ssh/**)`, `Edit(./secrets/**)`, `Edit(./.env)`,
  `Edit(./**/.env)`, and `Bash(git push * main)`, `Bash(git push *:main)`,
  `Bash(git push *:refs/heads/main)`, `Bash(git push * +main)`,
  `Bash(git push --force *)`, `Bash(git push -f *)`,
  `Bash(git push * --force*)`, `Bash(git push * -f *)`. Per the permissions
  page, `./` is relative to the session directory, `.env` matches that file
  name only, so `.env.example` stays readable, and `git -C . push` is not
  matched by these Bash rules, which the dispatcher covers instead.
- The PreToolUse hook now has `"onFailure": "block"` (Claude Code 2.1.295 or
  later; 2.1.296 installed) and a 30-second timeout; per the documentation a
  hook that times out then denies the tool, which is not observed. The Registry
  owns the value as the optional binding field `on_failure`, the contract
  loader accepts only `block`, and the parity test compares it with
  `settings.json`.
- The Provider Registry translates only role permission profiles, not these
  settings rules, so Codex has no matching file-read denial; Codex relies on
  its sandbox and approval policy, which cannot start here (W2).

### Review Round 1

On 2026-10-14 independent `rules-engineer`, `security-auditor` and
`ci-cd-engineer` reviews of `a16ca2451..f8af6b3ab` each returned FAIL.
Findings and their disposition:

- **Rules B1:** environment-constraints §1 prescribed `danger-full-access` for
  live Codex writes, which approval-boundaries forbids a policy to grant. It
  now records the limit only and names such a run a protected operation that
  needs per-run owner authorization (1.4.0).
- **Rules B2:** the unauthorized direct `pre-commit run`, recorded in W3; its
  evidence row is replaced.
- **Rules B3:** `onFailure` lived outside the Registry; moved there as above.
- **Rules N1–N5:** the Claude adapter (1.2.0) cites the secret boundary and
  the no-direct-push rule as the owners its deny rules back; documented but
  unobserved behaviour is marked so; the Codex observation is dated; the
  hookify rule's headings left the code block and its quote matches
  `github-governance.md`.
- **Security H1:** `git push -u origin HEAD` on `main` was allowed. `HEAD` and
  `@` now resolve to the current branch.
- **Security M1, M2, L2:** the dispatcher now follows `pushd`, subshells,
  `env`/`command` prefixes, `GIT_DIR`, `GIT_WORK_TREE`, `--git-dir` and
  `--work-tree`; treats `heads/main`, wildcard refspecs, `--branches` and a
  `-c` push setting naming `main` as pushes to `main`; and denies when the
  repository cannot be read. `git push --tags` alone is allowed.
- **Security M3 (residual):** `Edit(./**/.env)` was added. The `./` rules do
  not reach the main checkout's ignored `secrets/` and `.env` by absolute path
  from a linked worktree; the owner decides whether to add path-specific rules.
- **Security L1 and CI 1 (residual):** under the pre-commit shim the guard sees
  only the first pushed ref with new commits, so a multi-ref push that lists
  another branch first bypasses it; pre-commit also skips deletions and
  pushes it judges empty, and `--no-verify` skips it. The rule, Spec and this
  Task now state those limits; the dispatcher still denies the multi-ref text
  forms.
- **CI 2:** `check-added-large-files`, `end-of-file-fixer` and
  `trailing-whitespace` declare pre-push upstream; they are pinned to
  `[pre-commit, manual]` and a test checks it.
- **CI 3 (owner, host):** global `core.hooksPath` (`~/.codex/git-hooks`) makes
  `pre-commit install` fail on this host, so the guard is not installable here
  until the owner changes that user-global setting.
- **Not changed:** quoted text that contains a main push is denied (friction
  only); `--force-with-lease` on a feature branch stays denied, as the owner
  chose.
