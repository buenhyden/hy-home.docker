# Loki Usage Guide

## Overview

이 가이드는 `06-observability` 계층의 Loki 사용 맥락과 설정 확인 방법을 설명한다. Loki는 Alloy가 수집한 Docker 로그를 `http://loki:3100/loki/api/v1/push`로 수신하고, SeaweedFS S3 backend의 `loki-bucket`에 chunks/index를 저장하며, Grafana datasource `Loki`를 통해 LogQL query를 제공한다.

## Audience and Goal

대상 독자: 개발자, 운영자, SRE, AI Agent.

- Loki 서비스, custom image, SeaweedFS storage, retention, compactor, label cardinality, Alloy ingestion, Grafana 쿼리 경계를 빠르게 파악한다.
- LogQL 검색과 readiness 확인에 필요한 구현 위치를 연결한다.
- 장애 대응, restart, storage/ingestion 분류, 설정 rollback은 [RUN-0043](../runbooks/0043-loki.md)으로 넘긴다.

## Usage

사용 전에 다음을 확인한다.

- `infra/06-observability/loki/config/loki-config.yaml` 설정을 읽을 수 있는 권한.
- Docker Secret ID `seaweedfs_s3_loki_secret_key`와 environment reference `S3_ACCESS_KEY`가 준비되어 있어야 한다. Secret 값은 문서, 로그, task evidence에 기록하지 않는다.
- Alloy pipeline과 Grafana datasource가 현재 compose network에서 `loki:3100`을 가리켜야 한다.
- Grafana UI `https://grafana.${DEFAULT_URL}` 접근 권한.

일반 순서는 다음과 같다.

1. Compose service boundary를 확인한다.

   ```bash
   rg -n 'service: template-stateful-high|image: hy/loki:|container_name: loki|loki-data|S3_ACCESS_KEY|seaweedfs_s3_loki_secret_key|LOKI_HOST_PORT|LOKI_PORT|/ready|gateway-standard-chain@file,sso-errors@file,sso-auth@file' infra/06-observability/docker-compose.yml
   ```

2. Loki config boundary를 확인한다.

   ```bash
   rg -n 'bucketnames: loki-bucket|access_key_id: \\$\\{S3_ACCESS_KEY\\}|secret_access_key: \\$\\{S3_SECRET_KEY\\}|retention_enabled: true|retention_period: 168h|compaction_interval: 10m|retention_delete_delay: 2h|alertmanager_url: http://alertmanager:9093' infra/06-observability/loki/config/loki-config.yaml
   ```

3. Custom image 및 secret expansion boundary를 확인한다.

   ```bash
   rg -n 'FROM grafana/loki:|ENTRYPOINT \\[\"/docker-entrypoint.sh\"\\]|-config.expand-env=true|S3_SECRET_KEY|S3_SECRET_KEY_FILE|exec /usr/bin/loki' infra/06-observability/loki/Dockerfile infra/06-observability/loki/docker-entrypoint.sh
   ```

4. Log ingestion 및 query path를 확인한다.

   ```bash
   rg -n 'loki.source.docker|loki.write|url = \"http://loki:3100/loki/api/v1/push\"|com_docker_compose_project' infra/06-observability/alloy/config/config.alloy
   rg -n 'name: Loki|uid: Loki|url: http://loki:3100' infra/06-observability/grafana/provisioning/datasources/datasource.yml
   ```

5. Grafana Explore에서 LogQL query를 실행한다.

   - UI: `https://grafana.${DEFAULT_URL}`
   - Datasource: `Loki`
   - 예시 selection: `{service_name="grafana"}`
   - 예시 filter: `{service_name="grafana"} |= "error"`
   - 예시 aggregation: `count_over_time({service_name="grafana"}[5m])`

### Source-backed operating contract

- **목적/분류/출처**: `loki`는 `obs`/`logs`가 선택하는 `HOME` log store다. [Compose](../../../infra/06-observability/docker-compose.yml)와 [Loki config](../../../infra/06-observability/loki/config/loki-config.yaml)가 authoritative하다.
- **Flow/state**: Alloy가 logs를 push하고, Loki는 SeaweedFS bucket `loki-bucket`에 TSDB schema-v13 blocks/index를 저장하며, `loki-data:/loki`는 local working/cache/ruler state를 보관한다. Retention 설정은 168h지만 compactor markers는 `/tmp/loki/compactor`에 있어 persisted `/loki` 밖이다. Object-store marker prefix도 없다; recreation은 pending deletion 상태를 잃을 수 있고 `/loki` 백업만으로 완전한 복구를 주장할 수 없다.
- **Secrets/dependencies/security**: `S3_ACCESS_KEY`와 `seaweedfs_s3_loki_secret_key`로 SeaweedFS에 접근한다. SeaweedFS, Alloy, Grafana, Traefik과 선언된 network가 dependency다. Gateway 보호와 tenant/header 규칙은 일관되게 유지해야 하며, object-store credential은 출력하지 않는다.
- **Resources/normal use**: source의 limit은 headroom이 아니다. Root에서 render하고, config를 validate하고, readiness를 확인하고, labeled test log를 ingest해 query한 뒤 compactor/object-store error를 monitor한다.
- **Lifecycle**: storage owner와 함께 SeaweedFS bucket의 consistent backup을 조율하고 local recovery-relevant state/config를 보존한다. Point-in-time set을 위해 ingestion을 중지하거나 quiesce하고, 지원되는 schema/version transition으로 upgrade한 뒤 old/new query와 retention을 검증한다.
- **Upstream/license**: 공식 [Loki storage](https://grafana.com/docs/loki/latest/configure/storage/), [retention](https://grafana.com/docs/loki/latest/operations/storage/retention/), [upgrade](https://grafana.com/docs/loki/latest/setup/upgrade/) 가이드를 따른다. Loki는 AGPL-3.0 라이선스다.

### Approved LAN integration boundary

이 항목은 [POL-0043](../policies/0043-loki.md#approved-lan-integration-boundary)이 소유한다. 요약: Traefik hostname에는 TLS/SSO middleware를 유지한다. Loki HTTP `3100`은 [POL-0096](../policies/0096-k8s-integration.md#rules)의 기존 k3d 예외에 따라 `HOST_LAN_BIND_IP`(공개 기본값 `192.168.0.13`)에 gateway 인증 없이 게시된다. Loki `auth_enabled: false`는 사용자 인증이 아니고 Gateway middleware도 이 직접 포트를 보호하지 않는다. 기계 검증은 [GDE-0096](../guides/0096-k8s-integration.md)을 따른다. 재바인딩·제거·인증/TLS 추가·노출 확대는 통합 소유자와 조정한 별도 승인 변경이다.

### 운영 시 주의점

- **Label cardinality**: request ID, user ID, IP address 같은 동적 값을 label로 승격하면 index 비용과 query latency가 급증한다.
- **Secret evidence**: `S3_SECRET_KEY` 값이나 rendered env를 로그/evidence에 남기지 않는다.
- **Retention assumption**: 현재 retention은 `168h`이며 문서만 바꿔 보관 기간이 바뀐 것처럼 선언하지 않는다.
- **Alloy assumption**: Loki가 healthy여도 Alloy `loki.write`가 실패하면 Grafana에서 logs가 비어 보일 수 있다.
- **Direct access assumption**: 외부 UI route는 `https://loki.${DEFAULT_URL}`로 보호되고, 내부 compose network에서는 `loki:3100`를 사용한다.

### Common Checks

- `docker compose --profile obs ps loki`
- `docker logs --tail=100 loki`
- `docker exec loki wget -qO- http://127.0.0.1:3100/ready`
- `rg -n 'loki.source.docker|loki.write|http://loki:3100/loki/api/v1/push' infra/06-observability/alloy/config/config.alloy`
- `rg -n 'retention_enabled: true|retention_period: 168h|bucketnames: loki-bucket' infra/06-observability/loki/config/loki-config.yaml`
