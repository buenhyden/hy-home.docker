# n8n Usage Guide

## Overview

이 가이드는 `hy-home.docker`의 n8n 로우코드 자동화 환경을 사용하는 방법을 설명한다. 현재 구현은 `n8n`, `n8n-worker`, `n8n-task-runner-worker` queue mode 구성과 별도 `blog-ingestion` profile의 Blog-data 수집 Gateway `blog-ingestion`이다. `dedicated-valkey` profile은 dedicated `n8n-valkey`를 기동하지만, 실제 broker는 `N8N_VALKEY_HOST`/`N8N_VALKEY_SECRET` pair가 선택하며 기본값은 공유 `mng-valkey`다.

## Scope

### Audience and Goal

**대상**

- Developer
- Operator
- Integration Maintainer
- AI Agent

**목적**

- n8n UI, webhook, public API, queue worker 구성을 이해한다.
- workflow 작성, 테스트, 활성화, 오류 처리의 기본 흐름을 맞춘다.
- credential과 secret을 노출하지 않는 운영 경계를 유지한다.
- 반복 복구 절차는 paired runbook으로 넘긴다.

## Concepts

- `infra/07-workflow/n8n/README.md`의 service readiness 확인

## Usage

### 사용 절차

#### Architecture and Components

n8n은 확장성을 위해 분산형 큐 아키텍처를 사용하며, 주요 컴포넌트는 다음과 같다:

- **n8n Main**: 사용자 인터페이스(UI), API 서버, 워크플로우 엔진.
- **n8n Worker**: 대규모 비동기 작업 처리를 담당하는 작업 실행기.
- **n8n Task Runner**: `n8n-task-runner-worker`가 외부 runner 모드에서 worker의 broker endpoint에 연결한다. main은 수동 실행도 worker로 넘기므로 task runner를 시작하지 않는다(SPEC-0269).
- **Valkey Broker**: base source는 `infra/07-workflow/n8n/docker-compose.yml`이다. `dedicated-valkey` profile은 `n8n-valkey`와 exporter를 기동할 뿐이다. `${N8N_VALKEY_HOST:-mng-valkey}`와 `${N8N_VALKEY_SECRET:-mng_valkey_password}`가 실제 broker를 선택하며 두 값을 matching pair로 바꾸지 않으면 공유 `mng-valkey`가 유지된다. 선택형 공유 이름 계정은 아래 ACL overlay·username·DB 계약을 함께 따른다.
- **Metadata DB**: 워크플로우 레시피 및 사용자 자격 증명(`Credentials`)을 저장하는 PostgreSQL 데이터베이스.

#### Access and Integration

- **Web UI**: `https://n8n.${DEFAULT_URL}` 에 접속하여 시각적으로 자동화 로직을 설계한다.
- **Public API**: 필요한 경우 `N8N_PUBLIC_API_BASE_URL`을 통해 프로그래밍 방식으로 워크플로우를 제어할 수 있다.
- **Webhook**: `WEBHOOK_URL`은 URL을 지정한다. Host 기준 n8n router는 `gateway-standard-chain@file`만 적용하고 gateway SSO(`sso-auth`)는 두지 않으며, 인증 없는 `/metrics`와 Hermes webhook 경로(`/webhook/hermes-blog-ingestion` 접두)는 `!PathPrefix`로 제외해 게시하지 않는다(Prometheus는 `n8n:5678`을 내부에서 직접 수집한다). 로그인과 API 인증은 n8n 자체 인증이 맡는다(owner 결정, 2026-11-09). [hermes-webhook.yml](../../../../infra/01-gateway/traefik/dynamic/hermes-webhook.yml)의 `POST /webhook/hermes-blog-ingestion` 하나는 별도로 `HOST_LAN_BIND_IP/32` 출발지·1 MiB 본문·분당 6건 제한과 n8n header 인증을 적용한다. 그 밖의 UI·API·webhook 경로에는 n8n 자체 인증과 요청 본문 상한 `N8N_PAYLOAD_SIZE_MAX`가 앞단 통제의 전부이므로, SSO를 되돌리거나 경로를 더 열려면 별도 승인된 동적 구성이 필요하다.

#### Workflow Authoring and Activation

- 필요한 trigger/action node를 선택하고 node 간 data flow를 명시한다.
- 복잡한 변환은 `Code` node 또는 sub-workflow로 분리한다.
- 새 워크플로우 설계 시 `Manual Execution`으로 개별 노드의 데이터 입출력을 검증한다.
- 실패 알림이 필요한 workflow에는 error workflow 또는 notification node를 연결한다.
- 검증 완료 후 `Active`로 전환한다.

#### Credential and Secret Boundary

- 모든 인증 정보는 n8n 내부의 `Credentials` 탭에서 관리한다.
- credential은 metadata DB에 암호화되어 저장되며, `N8N_ENCRYPTION_KEY_FILE`은 Docker Secret으로 주입된다.
- workflow export, API response, screenshot evidence에는 credential value, token, webhook secret 원문을 포함하지 않는다.

#### Custom Node Extension

- 필요한 경우 `infra/07-workflow/n8n/custom` 경로에 사용자 정의 node를 추가할 수 있다. 이 경로는 main·worker에 읽기 전용으로 bind되므로 컨테이너가 tracked 폴더에 코드를 쓸 수 없고, 변경은 Git 검토 뒤 컨테이너 재생성으로만 반영된다.
- custom node 추가 전 security review와 root validation을 완료한다.

#### Development and Verification

- **Local Runner**: 새로운 노드나 복잡한 JS 코드는 n8n 내부의 `Code` 노드에서 직접 실행하여 즉시 결과를 확인할 수 있다.
- **Static Validation**: root network/secrets context의 Compose 검증과 hardening을 확인한다. service-local compose 단독 결과로 준비 상태를 판정하지 않는다.
- **Runtime Health**: main readiness, worker 등록과 runner 상태를 각각 확인한다. 실행 명령은 [Runbook](../../runbooks/08-workflows-and-automation/0053-n8n.md#verification)이 소유한다.

### Build, readiness and runner boundary

n8n에는 init job이 없다. Main/worker는 Compose의 `context: .`에 해당하는 `infra/07-workflow/n8n` context에서 `${N8N_DOCKERFILE:-dev.Dockerfile}`과 명시 version arg를 쓰며 target은 없다. Compose가 Dockerfile 기본값을 덮어쓴다. 두 recipe 모두 Alpine font-builder에서 fontconfig·Noto·DejaVu·Liberation font를 설치하고 font·cache·config를 최종 n8n stage로 COPY한다. 이 파일들은 CA/curl/jq를 설치하지 않는다. 기본 dev recipe는 `USER node`와 dev entrypoint를 사용하고 production 대안은 UID/GID를 확인한 `USER 1000`을 쓴다. 둘 다 `custom/`과 해당 entrypoint를 COPY한다. `n8n-data` volume이 image의 `/home/node/.n8n` 전체를 가리므로 image의 `custom/` 복사본은 실행 중 보이지 않고, 읽기 전용 bind가 tracked `custom/`을 전달한다. 이와 달리 별도 immutable Opsflow package는 `/opt/hyhome/n8n-custom/opsflow`에서 검증 후 user-folder nodes 경로로 연결한다. Compose `init: true`가 process init을 제공한다.

main/worker에는 선택한 broker secret 하나만 마운트된다. 두 entrypoint는 `N8N_VALKEY_HOST`/`N8N_VALKEY_SECRET`의 지원 쌍과 실제 선택된 secret 파일을 함께 검사한다. 이는 broker 인증 성공을 증명하지 않으므로 DB/broker readiness를 따로 확인한다.

선택형 공유 이름 계정은 `N8N_VALKEY_USERNAME=n8n`과 별도
`mng_valkey_n8n_password`를 MNG ACL overlay와 함께 선택한다. 기본 username 빈 값·
공유 Secret·DB0는 그대로이며 새 파일을 요구하지 않는다. `N8N_VALKEY_DB=0`은
기존 큐를 보존하고, 실제 Queue의 Host/User/Password file/DB도 같은 입력에서 파생한다.
다른 조합이나 별도 Queue 변수 덮어쓰기는 entrypoint가 거부한다. 이름 계정의
`n8n:*` key/channel과 DB0 command 후보는 실제 Bull queue 시험 전 최소 권한 수용이 아니다.

2026-10-26 확인한 고정 소스는 [n8n package](https://github.com/n8n-io/n8n/blob/ffbb9ec54fc02e7f8b54a0b6f41d0a84d0a817f5/packages/cli/package.json)의
Bull 4.16.4와 ioredis 5.3.2다. <!-- runtime-version-exception: compatibility — fixed queue ACL source assessment, not an update owner -->
[ScalingService](https://github.com/n8n-io/n8n/blob/ffbb9ec54fc02e7f8b54a0b6f41d0a84d0a817f5/packages/cli/src/scaling/scaling.service.ts)는
Bull을 생성하고 [RedisClientService](https://github.com/n8n-io/n8n/blob/ffbb9ec54fc02e7f8b54a0b6f41d0a84d0a817f5/packages/%40n8n/backend-services/src/services/redis-client.service.ts)는
단일 서버 prefix를 유지한다. [Bull queue](https://github.com/OptimalBits/bull/blob/65355b88838db6d36577c22ec7d4a876a70fad96/lib/queue.js)의
key는 prefix·queue name·type을 `:`로 연결하므로 현재 `n8n:jobs:*`와 pool queue도
`~n8n:*` 안에 있다. [Publisher](https://github.com/n8n-io/n8n/blob/ffbb9ec54fc02e7f8b54a0b6f41d0a84d0a817f5/packages/cli/src/scaling/pubsub/publisher.service.ts)의
제어 channel과 MCP session도 `N8N_REDIS_KEY_PREFIX=n8n` 아래다. entrypoint는 두
prefix 변경·cluster override를 거부한다. BullMQ의 다른 command를 추정해 허용하지 않는다.

명시 command 후보는 [Bull 배포 원본](https://registry.npmjs.org/bull/-/bull-4.16.4.tgz)의 <!-- runtime-version-exception: compatibility — reviewed source tarball identity, not a runtime selection -->
Lua 호출과 queue JS 연결·PubSub 호출, 위 Publisher의 get/set/del/expire를 대조했다.
원본 SHA256은 `a51664279f83fba1c993b224e3dd9075cb307de81be9baa24d375ae929cde137`이다.
전체 key 이름을 열거하는 `KEYS`/`SCAN`과 관리 명령은 허용하지 않아 bulk cleanup은
이 계정의 수용 범위가 아니다. 고정 n8n patch는 Job.finished 오류 처리를 바꾸며
배포된 실제 이미지·정상 업무·ACL LOG·부정 시험은 별도 확인해야 한다.

Local Ollama 연결은 선택형 `docker-compose.ollama-local.yml`이 Worker와 Ollama만
새 internal bridge에 추가한다. Main에서 Credential Test가 성공해도 Worker 실행
성공은 별도다. Code Runner에는 경로가 없고 기존 Ollama edge/AI peer 접근도 유지된다.
실제 저장된 Credential·Node를 값 없이 확인하고, Worker에서 모델 목록·생성·embedding,
실패·복구와 추가 망에 없는 peer 거부를 검증해야 한다. Cloud 키·HTTPS 전송·데이터·비용
승인이 없으면 `BLOCKED_CLOUD_APPROVAL`로 두며 `OLLAMA_NO_CLOUD=1`을 유지한다.
명령과 운영 전제는 [Runbook](../../runbooks/08-workflows-and-automation/0053-n8n.md#선택형-공유-valkey-계정과-local-ollama)을 따른다.

Compose의 main/worker와 두 runner는 [공식 external runner 버전 계약](https://docs.n8n.io/deploy/host-n8n/configure-n8n/set-up-task-runners/)에 맞춰 동일 릴리스로 선언했다. `N8N_RUNNERS_TASK_TIMEOUT`을 사용하고 runner launcher가 Docker secret 파일을 읽어 토큰을 환경 변수로 전달한다. 이는 정적 계약이며 JS/Python Code 노드, queue, migration의 격리 실행과 HOME 전환은 아직 검증하지 않았다. n8n 본체·runner·빌드 인자·로컬 이미지 태그는 한 묶음으로 수동 갱신하며 Renovate 자동 제안은 비활성화한다. 이 호스트에서는 runner가 cold start하는 데 약 40초가 걸렸다. 기본 grant token 유효 시간 30초를 넘겨 broker가 403으로 거절했고, 15초 동안 idle이면 runner가 종료되므로 하루 한 번 도는 작업은 매번 cold start가 된다. 그래서 main·worker에는 `N8N_RUNNERS_GRANT_TOKEN_TTL`(기본값 120)을, 두 runner에는 `N8N_RUNNERS_AUTO_SHUTDOWN_TIMEOUT: 0`을 지정해 첫 실행 이후 runner가 계속 떠 있게 한다.

### Blog-data 수집 Gateway

`blog-ingestion`은 Blog-data가 소유한 코드를 이 호스트에서 로컬 빌드한 이미지(`pull_policy: never`)로 실행하는 서비스다. `blog-ingestion` profile에만 속하므로 `workflow` 선택에 들어가지 않는다. `n8n_blog_ingest_net`으로 `n8n-worker`만, `blog_export_net`으로 Traefik만 peer가 되며, 외부 진입은 [blog-export.yml](../../../../infra/01-gateway/traefik/dynamic/blog-export.yml)의 출발지 제한 exact-path router만 허용한다. SQLite 수신 기록은 `${DEFAULT_WORKFLOW_DIR}/blog-ingestion/data`, Token SHA-256 다이제스트 설정은 `${DEFAULT_WORKFLOW_DIR}/blog-ingestion/config.json`(읽기 전용 bind)에 있고 두 경로는 미리 만들어야 한다. healthcheck는 인증 없는 `/v1/summary`의 401만 확인한다. 배치·백업·전환 절차는 [Runbook의 Hermes 수집 전송](../../runbooks/08-workflows-and-automation/0053-n8n.md#hermes-수집-전송-소스-단계-확인과-복구-경계)이 소유한다.

### Source-backed operating contract

- **목적·분류**: `n8n`, `n8n-worker`, `n8n-task-runner-worker`는 소유자가 확인한 `HOME` 자동화 서비스다. `n8n-valkey`와 해당 exporter는 `OPTIONAL` 전용 broker 쌍이다.
- **profile·구현 소유권**: 핵심 서비스는 `workflow`/`workflow-n8n`을 사용하고 전용 broker 쌍은 `dedicated-valkey`를 사용한다. [Compose](../../../../infra/07-workflow/n8n/docker-compose.yml)와 선택된 Dockerfile이 구현을 소유한다.
- **상태 흐름**: PostgreSQL database `n8n`은 `mng-pg`에서 workflow/execution metadata를 영속 저장한다. `n8n-data`와 `custom/`은 local application, binary와 extension artifact를 담고 Valkey는 queue 조율을 맡는다. 현재 task runner는 stateless/read-only root, tmpfs와 read-only launcher configuration을 사용한다. 이전 runner volume 선언은 rollback/data identity로 분리해 보존하지만 현재 runtime mount나 복구 성공 증거는 아니다. queue state만으로 복구 가능한 전체 workflow 이력을 구성할 수는 없다.
- **secret·환경 설정**: `n8n_db_password`, `n8n_encryption_key`, `n8n_runner_auth_token`, 전용 Valkey의 `n8n_valkey_password`(monitor ACL overlay를 쓰면 `n8n_valkey_monitor_password`)와 선택된 broker password를 보존한다. `N8N_VALKEY_HOST`와 `N8N_VALKEY_SECRET`은 함께 전환해야 한다. profile만 선택하면 기본값은 `mng-valkey`/`mng_valkey_password`로 유지된다.
- **의존성·보안**: PostgreSQL, 선택된 Valkey, Traefik이 준비되어야 한다. main은 `edge_net`·`n8n_net`·`mng_data_net`·`obs_net`, worker는 `n8n_net`·`n8n_worker_runner_net`·`mng_data_net`·`n8n_blog_ingest_net`, runner는 `n8n_worker_runner_net` 하나에만 연결된다. Qdrant와 다른 API는 이를 사용하는 workflow에만 의존성이다. Compose는 custom CA를 mount하지 않는다. entrypoint의 인증서 loading은 `/opt/custom-certificates`가 별도로 제공된 경우에만 이루어진다. task runner는 내부에 두고 auth token을 사용하며, UI는 gateway 표준 체인과 n8n 자체 로그인을 사용하고 gateway SSO(ForwardAuth)는 두지 않는다.
- **영속성·자원**: PostgreSQL과 이에 맞는 encryption key를 local data, custom node, 외부에 저장한 binary artifact와 함께 복구한다. Compose limit은 source 선언이며 측정된 여유 용량이 아니다.
- **정상 사용·수명 주기**: 저장소 root context에서 렌더링을 검증한다. backup이나 update 전에 schedule/webhook과 외부 producer를 비활성화하고 실행을 drain하고 상태를 대조·정리한다. PostgreSQL과 artifact를 일관되게 backup하고 upstream 순서에 따라 upgrade한다. 재개 전에는 credential, 수동 workflow, queue worker, webhook과 task runner를 검증한다.
- **공식 문서·license**: 공식 [queue mode](https://docs.n8n.io/deploy/host-n8n/configure-n8n/scaling/enable-queue-mode/), [encryption key](https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/configuration-examples/set-a-custom-encryption-key/), [backup/restore](https://docs.n8n.io/deploy/host-n8n/keep-n8n-running/backup-and-restore/), [update](https://docs.n8n.io/deploy/host-n8n/keep-n8n-running/update-n8n/) 지침을 따른다. n8n에는 Sustainable Use License/fair-code 조건이 적용되므로 고정된 release의 조건에 맞는 사용인지 확인한다.

### 독립 DEV 매니페스트 통지

[전용 워크로드](../../../../infra/07-workflow/n8n/workloads/manifest-outbox-notifier/README.md)는
DEV outbox를 소비하는 비활성 공개 JSON과 제한된 SMTP node입니다. SPEC-0204 C19/C22의
당시 queue·수동/예약·불확실 전송·복원 수용은 보존합니다. 현재 source/image/private
workflow 동등성과 P05의 신규 재처리·STARTTLS 증거는
[Task0044](../../../03.specs/0212-request-baseline-and-reconciliation/tasks/tsk-0044-opsflow-notifier-recovery.md)에서
별도로 기록합니다. 과거 실패만으로 이후 수용을 취소하거나 과거 수용을 현재 HOME
PASS로 확대하지 않습니다. public JSON의 credential placeholder는 공식 UI/API의 private
실행 사본에서만 해결합니다. 환경 파일 변경은 저장 credential 갱신 증거가 아닙니다.
동일 credential ID를 공식 경로로 갱신한 뒤 다음 실행이 새 material을 조회하는지 확인하며,
이 검증을 P06의 실제 비밀 발급·정본·운영 회전으로 승격하지 않습니다.

기본 `mailpit-plain-v1`과 선택형 `mailpit-starttls-auth-v1`은 고정된 `mailpit:1025`만
허용합니다. 인증 profile은 STARTTLS·인증·CA와 이름 검증을 요구하고 downgrade를
허용하지 않습니다. 실제 외부 SMTP 경로를 추가하지 않습니다. 성공 표시는
accepted_by_smtp이며 외부 배달이나 exactly-once가 아닙니다. 수락/ack 불확실은 unknown으로
보존하고 개별 승인·no-send 증거 없는 dead 재처리는 금지합니다.

선택 notifier는 `input.binary`를 거부하며 신규 binary 저장소를 추가하지 않습니다.
고정 n8n source의 [binary 설정](https://raw.githubusercontent.com/n8n-io/n8n/n8n%402.46.6/packages/core/src/binary-data/binary-data.config.ts)은 <!-- runtime-version-exception: compatibility — immutable selected-release source assessment, not a deployment pin -->
mode가 미지정이면 queue에서 database, regular에서 filesystem을 선택합니다.
환경 override와 실제 설치 이미지·사설 workflow는 별도 확인 대상이며 최신 generic 문서의
기본값을 고정 release에 일괄 적용하지 않습니다.

### 격리 native 검증의 범위

UNIT·합성 계약 검사, 실제 이미지 로딩, 격리 queue 실행과 HOME 적용은 별도 증거입니다.
기본 unittest 실행은 두 opt-in native class를 skip합니다. 명시 선택자가 있으면 정확한
고정 캐시 image ID·default context와 실행 경계를 검사하며 일부 선택자만 설정해도 실패합니다.
선택자·실행 순서·중단·정리 절차는 [Runbook의 격리 native 검증](../../runbooks/08-workflows-and-automation/0053-n8n.md#격리-native-검증)을 따릅니다.

| 범위 | 확인한 결과와 한계 |
| --- | --- |
| production 이미지 build·실제 custom node 로딩 | Task0017의 ISOLATED PASS. 같은 base peer 해석과 font를 확인했으며 dev recipe를 별도로 빌드한 결과는 아닙니다. |
| n8n 전체 queue·SMTP·복원 | 초기 readiness/cleanup 실패는 이력으로 보존합니다. 이후 SPEC-0204 Task0013의 C19/C22 수용은 당시 고정 이미지·Criterion 범위로 재사용하며, 현재 P05 추가 source/native 증거는 Task0044가 별도 소유합니다. |
| Airflow Celery 게시·빈 대상 복원 | Task0020은 migration role·내부 원인 미상·pg_hba 오류 이력을 보존합니다. Task0020 당시 V6는 worker의 PutObject InternalError로 ERROR였으며 Seaweed 내부 원인은 UNKNOWN입니다. Docker 잔여는 없고 자동 cleanup FAIL은 보호된 진단 보존으로, 별도 reconciliation·독립 확인 상태는 Task0020이 소유합니다. 당시 게시 수용·복원은 미검증입니다. 현재 P04의 full S3 permission FAIL582.770초와 narrow retry ERROR190.468초는 [Task0043](../../../03.specs/0212-request-baseline-and-reconciliation/tasks/tsk-0043-opsflow-data-path.md)의 TEST_RESIDUAL로 별도 보존합니다. |
| 같은 데이터의 생산자→소비자 인계 | 별도 fixture의 독립 게시·소비 시험만으로 입증할 수 없습니다. Airflow가 만든 outbox 데이터를 n8n에 인계하는 시험이 남아 있습니다. |

각 fixture는 합성 자산만 사용하고 같은 직렬 lock을 공유합니다. 한 fixture의 종료와
정리를 확인한 뒤 다음 fixture를 실행하므로 두 stack의 동시 기동을 전제로 하지 않습니다.
기존 SQL native 시험의 PostgreSQL 18.6 논리 dump/restore는 제한된 DB 증거입니다. <!-- runtime-version-exception: compatibility — fixed isolated SQL fixture input, not a HOME or Timescale deployment pin -->
실제 DEV Timescale 이미지, n8n metadata와 동일 encryption key의 복원, HOME·물리 백업·
offsite 복구를 대신하지 않습니다. admission·capture·cleanup 통제는
[Policy](../../policies/08-workflows-and-automation/0053-n8n.md#격리-native-실행-수용)가 소유합니다.

## Troubleshooting

- 대규모 배치/의존성 DAG를 n8n에 넣어 worker queue를 장시간 점유하는 경우. 이 경우 Airflow로 분리한다.
- workflow가 많은 node를 포함해 유지보수가 어려워지는 경우. `Sub-workflows`로 분리한다.
- webhook을 외부에 노출하면서 gateway allowlist, SSO, rate-limit 경계를 검토하지 않는 경우.
- service-local compose를 root network/secrets context 없이 단독 readiness evidence로 사용하는 경우.
