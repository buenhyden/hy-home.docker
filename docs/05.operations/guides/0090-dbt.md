# dbt Usage Guide

## Usage

### Purpose and classification

dbt는 `analytics-engineering`이 선택하는 OPTIONAL command-line 변환
작업이다. web UI가 없으므로 route나 OIDC client가 없고 필요하지도
않다.

### Current implementation

- [dbt Compose](../../../infra/12-analytics/dbt/docker-compose.yml)는 feature
  SQL을 실행하는 `dbt-db-provision`과 `dbt` job을 정의한다.
- role `DBT_DB_USER`는 `DBT_DB_NAME`(기본값 `SERVICE_POSTGRES_DB`)에
  연결한다. application owner가 나중에 생성한 table을 포함해 `DBT_SOURCE_SCHEMA`를
  읽을 수 있고 `DBT_SCHEMA`를 소유한다. schema를 생성하거나 source schema에
  쓸 수는 없다.
- project와 profile은 read-only mount이다. `target/`, `logs/`, `packages/`는
  job의 `/tmp` tmpfs에 있으며 container와 함께 사라진다.
- project는 connection과 target-schema write access를 증명하는 smoke view인
  `hyhome_dbt_connectivity`만 제공한다. 비즈니스 model은 아직 정의되지
  않았다.

### Identity-specific behavior

dbt core1.11.15/postgres1.11.0, Python3.12, mounted profile/project 와 secret wrapper 가 실제 실행 입력이다. dbt-db-provision 은공유 runner 로 role/CONNECT/sourceSELECT/target-schema 권한을 변경한다. 입력오류/timeout64 와 SQL3/다른 shell 오류를 구분하며 ON_ERROR_STOP 도이전 DDL 을 rollback 하지 않는다. `debug`/기본 smoke view 성공을모든 model 실행으로 확대하지 않는다. `test`/`compile`도미래 custom macro·hook 까지무조건읽기전용이라는계약은아니므로 model/code review 가필요하다.

| 정확한 식별자 | 목적·상태·기동 차이 | 준비 상태 판단의 한계 | 구현 소유자 |
| --- | --- | --- | --- |
| `dbt` | one-shot CLI; debug 기본, model run/build는 DDL/DML | HTTP health 없음; 종료 코드와 읽기/검증 결과 확인 | [선택·의존·접속·입력·mount](../../../infra/12-analytics/dbt/docker-compose.yml) |
| `dbt-db-provision` | target schema/source SELECT feature provisioning job | HTTP health 없음; 종료 코드와 변경된 대상의 실제 상태 확인 | [선택·의존·접속·입력·mount](../../../infra/12-analytics/dbt/docker-compose.yml) |

선택 profile, version, port, 환경 입력, secret identifier와 mount의 정확한 값은 각 행의 구현이 소유한다. [공통 template](../../../infra/common-optimizations.yml)의 resource·security 상속과 서비스 override를 함께 읽는다. 값의2026-10-01 source snapshot과 official version/build 검토는 [W4 Task](../../98.archive/completed/03.specs/0198-operations-documentation-system/tasks/tsk-0004-data-messaging-analytics.md)에 보존했다. 반복OOM, disk/WAL/checkpoint 증가와 metrics 누락은 capacity 검토 trigger이며 health는 사용자 기능이나 복원을 증명하지 않는다.

### Commands and side effects

아래 진단은 mng-pg가 healthy이고 base/feature provisioning이 이미 완료된 승인 환경에서만 수행한다. 미완료라면 중단하고 [dbt runbook](../runbooks/0090-dbt.md#procedure)의 named provisioning 승인을 따른다. `--no-deps`는 `dbt-db-provision`과 `mng-pg-init`의 암묵 실행을 막으며 최초 provisioning을 대신하지 않는다. 표는 client/model의 효과를 설명한다. `run`/`build` 및 사용자 hook·macro의 쓰기 효과는 별도로 승인해야 한다.

| 명령 | Database에 미치는 영향 | 입증하는 내용 |
| --- | --- | --- |
| `dbt --version` | 없음 | image가 시작함; database에 대해서는 아무것도 증명하지 않음 |
| `dbt debug`(기본값) | connection을 염 | profile과 credential이 동작함 |
| `dbt compile` | Read-only introspection | SQL이 catalog에 대해 render됨 |
| `dbt run` / `dbt build` | `DBT_SCHEMA`에 relation을 생성/교체함; `build`는 test도 실행 | 선택된 model이 materialize됨 |
| `dbt run --full-refresh` | incremental model을 drop하고 재구축 | 재구축; 오래 걸릴 수 있고 incremental 상태를 잃음 |
| `dbt test` | Read query | data test 통과 |

`docker compose --profile core --profile analytics-engineering run --rm --no-deps dbt <command>`로
command를 실행한다. `dbt test --store-failures`는 audit schema에 대한
`CREATE` 권한이 필요하지만 이 권한은 의도적으로 부여하지 않았다.
