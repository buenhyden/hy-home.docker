## Usage

### Usage

k6는 `testing`에서만 선택되는 **DEV** one-shot load generator다. Root Compose의
`k6`는 `version`만 실행하는 fail-closed inventory/render job이며 트래픽을 만들지
않는다. 승인된 합성 실행 인터페이스는 `quality_run.py`가 검증한 전용 internal Docker
network와 명시된 WireMock peer만 받는다. `--guard-config` 없이 호출하면 executor는 container를 시작하지 않고 `interrupted/path_confinement_unavailable`로 fail closed한다. `prepare-guard`로 만든 승인된 exact-path guard config가 있을 때만 합성 traffic을 실행하며, live target traffic 승인([SPEC-0204](../../03.specs/0204-service-integration-security-and-operations/spec.md))은 `BLOCKED`다. Port를 publish하지
않으며 health state도 없다.

### Implementation Sources

- [k6 Compose](../../../infra/11-quality/k6/docker-compose.yml)
- [k6 Dockerfile](../../../infra/11-quality/k6/Dockerfile)
- [k6 dashboard](../../../infra/06-observability/grafana/dashboards/Infrastructure/k6.json)
- [relay controller](../../../infra/11-quality/k6/metrics_relay.py)와 [relay 설정](../../../infra/11-quality/k6/metrics-ingress.alloy)

Dockerfile과 Compose 선언이 image version을 소유한다. `quality_run.py`의 versioned
manifest가 run identity, scenario hash, target, redirect policy, budget, threshold와
mock mode를 소유한다. `restart: "no"`는 root inventory job의 재실행을 막는다.
Compose에는 기존 Prometheus remote-write 환경 선언이 남지만 `version` job과 격리
executor는 이를 소비하지 않는다. manifest v2의 `telemetry.mode=otlp`이면 k6 OTLP metric이 run별 `metrics-ingress` relay를 거쳐 HOME Alloy의 인증된 수신기(4319)와 Prometheus로 간다(SPEC-0214). relay는 `quality_run.py run`에 `--relay-image`·`--relay-token-file`·`--metrics-egress-network quality_otlp_net`을 주면 controller(`metrics_relay.py`)가 만들고, 실행이 끝나거나 취소·timeout되면 그 attempt의 relay와 runner만 지운다. HOME 전달 확인 결과는 [SPEC-0214 TSK-0002](../../03.specs/0214-quality-k6-locust-and-otel-semantics/tasks/tsk-0002-relay-controller-and-locust-lifecycle.md)가 기록한다. render 성공이나 선언된 dashboard는
metrics 전달·보존 증거가 아니다.

### Normal Use

1. Target owner와 함께 target, traffic ceiling, stop condition, manifest, scenario
   revision과 격리 Docker context를 검토한다. root `k6` service에 command를 덮어써
   실행하지 않는다.
2. Project root에서 static check만 실행한다.

   ```bash
   bash scripts/hardening/check-all-hardening.sh 11-quality
   HYHOME_COMPOSE_PROFILES=testing bash scripts/validation/validate-docker-compose.sh
   ```

3. 승인된 isolated test는 [k6 Runbook](../runbooks/0061-k6.md)의 준비·중단 경계를
   따른다. guard config 없이 실행하면 preflight 뒤
   `interrupted/path_confinement_unavailable`으로 끝나며 traffic을 시작하지 않는다.
4. Finalizer가 만든 정제된 summary, exit metadata, final verdict를 target-side
   recovery signal과 함께 확인한다. raw stdout/stderr, request body, credential,
   cookie, URL query를 evidence로 남기지 않는다.

### State and Upgrade

실행 순서와 실패·복구 판단은 [런북](../runbooks/0061-k6.md)의 `시나리오 보존과 업그레이드` 절차를 따른다. 데이터와 권한 경계는 해당 정책을 유지한다.

### Common Checks

- `bash scripts/hardening/check-all-hardening.sh 11-quality`
- `HYHOME_COMPOSE_PROFILES=testing bash scripts/validation/validate-docker-compose.sh`
- `python3 infra/11-quality/k6/quality_run.py --help`
- remote-write declaration, Grafana dashboard 또는 root `k6` exit만으로 전달·보존을
  판정하지 않는다.

### Runbook Handoff

- [k6 Runbook](../runbooks/0061-k6.md)이 승인된 isolated run의 중단·복구 경계를
  소유한다.

### 실행 경계와 한계

root `k6`는 `obs_net`에만 선언되며 대상이나 WireMock을 자동으로 기동하지 않는다.
격리 executor는 승인된 전용 network, 단일 labeled WireMock peer, read-only scenario
snapshot, 별도 result file과 CPU·메모리·PID 상한을 검사한다. 작업 종료 코드, threshold
결과, final evidence state, target 회복, metric 전달은 서로 다른 신호다. `Infrastructure/k6`
dashboard는 OTLP 경로의 `k6_` series와 `instance=<run_id>-a<attempt>`를 조회한다. live
Grafana 확인 결과는 TSK-0002가 기록한다.

### 지표 경로의 신뢰 경계

- k6 container는 token도 Alloy 주소도 받지 않는다. token 파일은 relay에만 읽기 전용으로
  mount된다. controller는 다른 사용자가 읽을 수 있는 token 파일을 거부하므로 파일 권한은
  `0640` 이하로 둔다.
- relay는 producer가 보낸 resource 속성을 모두 지우고 manifest의 project·환경과
  `<run_id>-a<attempt>` instance를 붙인다. 시나리오가 relay에 OTLP를 직접 보내도 다른
  project나 run의 값으로 기록되지 않는다. 같은 run 안에서 지표 값을 꾸미는 것은 막지 못한다.
- 모든 relay가 token 하나를 공유한다. token을 가진 쪽은 어떤 project 이름도 붙일 수 있다.
  project별 자격 증명, 서버가 강제하는 project label, token 교체와 quota는 통합 작업
  ([SPEC-0204](../../03.specs/0204-service-integration-security-and-operations/spec.md),
  prompt 04)이 맡는다.
- relay는 run network와 internal `quality_otlp_net` 두 망에만 붙는다. `quality_otlp_net`에는
  Alloy와 relay만 있으므로 relay는 Alloy 4319 외의 곳으로 나가지 못한다.

### 지표 경로의 예산

| 항목 | 값 | 의미 |
| --- | --- | --- |
| remote write `sample_age_limit` | 5분 | Prometheus가 5분 넘게 응답하지 않으면 그동안 쌓인 표본은 버린다 |
| delta→cumulative `max_stale` | 5분 | 5분 동안 표본이 없는 stream은 상태를 잃고 다음 표본부터 새로 센다 |
| delta→cumulative `max_streams` | 10000 | 넘는 stream은 버린다. attempt마다 새 `instance` series 묶음이 생긴다 |
| Prometheus 보존 | 15일(기본값) | 그보다 오래된 run 지표는 `perf_db` 결과와 artifact로만 남는다 |

attempt 하나가 만드는 series 수는 실제 실행에서 잰 값을 TSK-0002에 기록한다.
`max_streams`를 그 수로 나눈 값이 5분 안에 동시에 보낼 수 있는 attempt 수의 상한이다.

### Dashboard 해석

- 지연 시간은 `histogram_quantile`을 bucket 합계에 적용한 값이다. 이미 계산된
  percentile을 평균하지 않는다.
- k6는 iteration이 버려졌을 때만 `dropped_iterations`를 보낸다. dashboard는 run이
  iteration을 보고했고 버린 것이 없으면 0을, run 자체가 없으면 값 없음을 보여 준다.
- check가 없는 시나리오는 `k6_checks_total`을 보내지 않는다. Checks 패널은 이때 0%가
  아니라 "No checks reported"를 보여 준다.
