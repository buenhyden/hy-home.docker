# dbt Operations Policy

## Purpose

### Objective

dbt는 application 데이터베이스에 파생된 relation을 기록한다. 그 권한은 source 읽기와
target schema 소유로 제한해야 한다.

### Authority

- [Analytics architecture](../../../02.architecture/descriptions/0012-data-analytics-architecture.md)
- SPEC-0262 Analytics labs migration
- [Image Dockerfile](../../../../labs/dbt/Dockerfile) and [derived version projection](../../../../infra/tech-stack.versions.json)
- [dbt Compose source](../../../../labs/dbt/docker-compose.yml)

## Scope

### Applies To

Provisioning, grant, 부작용이 있는 명령어, credential, 제거.

### Exclusions

dbt를 장기 실행 서비스로 만드는 것과 그 서비스용 OIDC web front end는 이 정책의 대상이 아니다.

## Rules

### Requirements

- 독립 LAB `labs/dbt/docker-compose.yml`의 `lab-dbt` profile로만 선택한다(SPEC-0262). root
  include와 HOME network 합류를 금지한다. dbt를 장기 실행 서비스로 만들거나 그런
  서비스용 OIDC web front end를 추가하지 않는다.
- HOME dev-pg는 `LAB_DBT_DB_HOST`/`LAB_DBT_DB_PORT` 입력으로만 지정한다. 소유자가 LAB에서
  도달 가능한 endpoint를 승인하기 전까지 HOME database port를 LAB network나 host에 임의로
  게시하지 않는다(미결정, 별도 승인).
- dbt grant는 `dev-platform-provision`이 아니라 feature provisioning SQL에 있다. role은
  `NOSUPERUSER NOCREATEDB NOCREATEROLE NOREPLICATION`이며 절대 source schema를
  소유하지 않는다. target schema는 source schema와 달라야 한다.
- `run`, `build`, `--full-refresh`는 검토된 model selection이 필요하다. `--version`이나
  `debug` 출력은 절대 model run으로 기록하지 않는다.
- 프로젝트와 profile은 read-only로 유지한다. 생성된 artifact는 tmpfs에 남는다.

#### Accountable lifecycle boundary

적용 identity: `dbt`, `dbt-db-provision`. 문서의 정적 검증과 runtime 운영 승인을 분리한다. @buenhyden이 named consumer·target·중단 영향·보존 기간과 예외를 소유한다. service image/profile/port/secret/mount, DDL·init, capacity 또는 backup 범위 변경 시 이 Policy와 linked Guide/Runbook을 함께 검토한다. engine secret/certificate는 이 subject의 credential 계약을, 앱 인증 연동은 적용되는 [POL-0079](../03-identity-and-access/0079-application-auth-integration.md)를, source 반영·재기동은 [POL-0006](../01-common/0006-infrastructure-optimization-governance.md#source-and-lifecycle-boundary), 보존·삭제는 [POL-0021](../10-platform-and-backup/0021-backup-and-restore.md)의 적용 통제를 따른다. exporter와 stateless job 자체에는 database restore가 없지만 설정·credential와 그 작업이 변경하는 upstream state는 제외되지 않는다. 소유 artifact·복구 지점·expiry가 불명확하면 삭제/재생성을 중단한다. 기존 Exceptions 외의 새 예외는 승인된 것으로 간주하지 않는다.

### Enforcement

정적 렌더링과 provisioning 테스트. 일회성 리허설로 source 읽기, target 쓰기,
source schema 거부를 증명한다.

## Exceptions

### Exception Conditions

없음. grant를 넓히려면(예: 데이터베이스에 대한 `CREATE`) 이유를 명시한 검토된
변경이 필요하다.

### Approval and Review

dbt나 adapter 업그레이드, 신규 source, grant 변경 시 검토한다.
