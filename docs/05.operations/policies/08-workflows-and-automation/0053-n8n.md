# n8n Operations Policy

## Overview

이 문서는 n8n 서비스의 안정적인 운영을 위한 정책과 통제 항목을 정의한다. 현재 구현은 `n8n`, `n8n-worker`, `n8n-task-runner`, `n8n-task-runner-worker` queue-mode 구성을 기준으로 한다. `dedicated-valkey` profile은 `n8n-valkey`를 기동하지만, 실제 broker는 `N8N_VALKEY_HOST`/`N8N_VALKEY_SECRET` pair가 선택하며 기본값은 공유 `mng-valkey`다.

## Scope

- **Systems**: n8n main/worker/task runner, PostgreSQL metadata DB connection, Valkey queue broker, Docker Secrets, Traefik route
- **Environments**: 로컬·개발·홈랩 운영

## Rules

- **Required**:
  - `EXECUTIONS_MODE: queue`와 external runner mode를 유지한다.
  - n8n credential material은 Docker Secrets 또는 n8n encrypted Credentials에만 둔다.
  - `dedicated-valkey` profile 선택 여부가 만드는 broker 차이(`mng-valkey` vs `n8n-valkey`)를 운영 문서에 명시한다.
  - workflow 변경 전/후 root validator와 hardening gate 결과를 기록한다.
- **Allowed**:
  - UI Export/API 기반 workflow JSON 백업 절차 문서화.
  - `./custom` 경로를 통한 사용자 정의 노드 추가, 단 보안 검토와 재검증 후 적용.
  - n8n workflow Git backup/OpenBao credential 연계의 단계적 강화.
- **Disallowed**:
  - plaintext credential, token, workflow secret 원문 문서화.
  - 승인 없는 gateway/SSO middleware 완화.
  - root network/secrets context 없이 service-local compose 단독 `config` 결과를 CI evidence로 주장.

### Lifecycle and data controls

- n8n 코어는 HOME, 전용 Valkey pair는 OPTIONAL을 유지한다. Broker 전환에는 matching `N8N_VALKEY_HOST`/`N8N_VALKEY_SECRET`, 실행 drain·부작용 조정과 rollback 근거가 필요하다.
- DB, 같은 `n8n_encryption_key`, 로컬/binary data, custom node와 외부 binary store를 한 복구 계약으로 다룬다. 다른 키로 credential 행을 복원하지 않는다.
- Backup/restore/update/migration 전에 schedule·webhook·producer를 멈춘다. Runner token 인증과 내부 전용 route를 유지한다.
- 별도 project/network에서 외부 업무 부작용을 차단하고 credential 복호화, worker/runner 등록·인증, manual workflow와 시험 webhook을 검증한 뒤 유입을 재개한다.
- 한도를 여유 용량으로 해석하지 않는다. 제거에는 workflow/credential export, 복구 자산 보존, OAuth/webhook client·secret 폐기와 데이터 삭제 승인이 필요하다.

### Declared implementation limitations

Runner 호환성 수용 전에 main/worker와 두 runner 버전이 일치해야 한다. 현재 선언은 정렬됐고 timeout key도 지원되는 복수형으로 바뀌었으나 JS/Python canary와 DB upgrade 검증은 남아 있다. 선택한 broker secret 하나만 마운트하고 entrypoint에서 지원 host/secret 쌍과 파일을 검사한다. 이 검사는 실제 broker 인증 성공의 증거가 아니다. Runner token이 launcher 환경 변수에 들어가므로 같은 컨테이너의 Code 작업이 `/proc`을 통해 token에 접근하지 못하도록 격리 통제를 확인하기 전에는 HOME 적용을 수용하지 않는다. matching DB/encryption-key 복구와 proxy SSO를 유지한다.

### 독립 outbox 소비자 경계

SQL·migration·claim/ack/retry·role·dead requeue는 P04가 단독 소유합니다. notifier에는
검토된 함수 EXECUTE만 허용하며 owner·superuser·직접 table write 권한을 부여하지 않습니다.
Mailpit 전용 host·port와 합성 송수신 주소만 허용하고 CC/BCC·첨부·file/URL 읽기·임의
header·외부 relay는 차단합니다. 기존 Stalwart 공유 mail network는 전용 capture 경계가
아닙니다. 실제 DB/mail node executor만 승인된 DEV/capture 접속 경계를 받습니다.
native credential·lease token·원문 driver 오류를 export·로그·evidence에 남기지 않습니다.
success/error/manual 실행 데이터 저장과 pinData를 끕니다. 운영 중 metadata와 encryption
key는 같은 신뢰 경계에 있으며 network placement가 관리자 credential 접근을 제한하지는 않습니다.
Message-ID는 run-derived 진단 식별자이며 exactly-once 보장이 아닙니다.

### 격리 native 실행 수용

- **소유자·대상**: @buenhyden이 승인한 합성 자산·exact image ID·source closure만 사용한다. 고정 캐시가 없거나 source/image가 다르면 HOLD한다. 시험 과정에서 자동 pull·HOME volume·운영 credential·외부 통지 경로를 사용하지 않는다.
- **직렬 실행**: 두 fixture는 공통 lock과 양쪽 attempt 소유권 sweep을 사용한다. stale 자원·lock·정리 상태가 불명확하면 새 실행을 시작하지 않는다. 다른 stack과 겹쳐 실행하지 않는다.
- **자원**: 기동 전 MemAvailable 7GiB, 실행 중 Docker 호출 전 3GiB, 사전 `/tmp` staging 여유 10GiB·inode 10%를 요구한다. container별 memory·CPU·PIDs·tmpfs·read-only·cap-drop 통제를 확인하고 memory-swap을 memory와 같게 하여 추가 swap을 허용하지 않는다. SwapFree 값은 관측하며 별도 고정 하한으로 수용을 판단하지 않는다.
- **압력**: 담당 coordinator는 bounded pre/post 관측에서 memory PSI full avg10·avg60이 모두 0이고 관측 구간의 oom_kill·pswpout 증가가 0임을 확인한다. full total microseconds와 그 차이는 기록용이며 양의 total 차이만으로 중단하지 않는다. fixture의 Docker 호출 전 RAM/cap 검사와 전후 압력 수용은 별도 통제이며 연속 watchdog이나 호출 도중의 무압력 보장이 아니다. 관측이 없거나 한도를 위반하면 HOLD한다.
- **시간·증거**: Runbook의 재현 가능한 capture 절차로 작업 780초·controller 900초와 cleanup 예약 120초를 제한한다. private 디렉터리·제한된 regular file·상속되는 출력 파일 한도·종료 후 정확한 잔여 자원을 확인한다. 원문 credential·workflow payload·무제한 로그를 공개 증거로 남기지 않는다. timeout만으로 detached Docker 자식 제거를 보장하지 않는다.
- **정리·수용**: command exit만으로 PASS하지 않는다. 업무 assertion과 cleanup이 모두 PASS이고 소유 자원이 남지 않아야 한다. 자동 cleanup FAIL은 후속 정확한 reconciliation PASS로 덮어쓰지 않는다. 실패·누락·잔여 자원은 HOLD이며 전체 prune·공유 volume reset·다른 소유자 자원 제거를 금지한다.
- **진단 보존**: 의도적인 protected evidence 보존과 live Docker 잔여를 구분한다. Docker 잔여가 없어도 기록된 attempt·private 증거·barrier를 유지한 cleanup FAIL이면 HOLD한다. 지정 검토자의 독립 zero 확인·좁은 원문 검사·기록된 identity/SHA에 따른 정확한 reconciliation 전에는 삭제하거나 반복 실행하지 않는다.
- **복원 범위**: 기존 SQL fixture의 합성 PostgreSQL 논리 dump/restore와 metadata 복원, 실제 DEV Timescale·HOME·물리·offsite 복구를 구분한다. 별도 두 fixture의 PASS를 같은 데이터의 end-to-end 인계 성공으로 수용하지 않는다.
