# n8n Runbook

## Overview

이 런북은 n8n 서비스 장애 발생 시 운영자가 신속하게 서비스를 복구하기 위한 단계별 절차를 제공한다. 현재 구현은 `n8n`, `n8n-worker`, `n8n-task-runner`, `n8n-task-runner-worker`를 기준으로 하며 실제 `N8N_VALKEY_HOST`/`N8N_VALKEY_SECRET` pair로 broker를 식별한다. Profile은 전용 pair를 기동할 뿐 선택을 바꾸지 않는다.

> Scope: n8n (07-workflow)

- n8n 서비스의 가용성 조기 회복
- 자동화 워크플로우 중단 시간 최소화
- 시스템 정상 작동 여부 검증

## Trigger

- n8n UI 접근 시 "Connection lost" 또는 50x 에러가 발생할 때.

## Prerequisites

### Trigger and Preconditions

- 워크플로우가 실행되지 않고 `Pending` 또는 `Waiting` 상태에 멈춰 있을 때.
- 워커 컨테이너가 반복적으로 재시작(`Restarting`)될 때.

### Service lifecycle prerequisites

최초 기동·upgrade 전에 실제 Dockerfile 선택, DB·broker 준비, encryption key·runner token 참조, mount 권한과 core/runner 버전 일치를 확인한다. 현재 선언은 같은 릴리스로 정렬됐지만 격리 Code 노드와 DB upgrade 검증 전에는 HOME 적용을 중단한다. main readiness 뒤 worker·main runner를, worker health 뒤 worker runner를 검증한다. 독립 init 서비스는 없다. 두 runner는 Code 실행기이며 DB 백업을 대체하지 않는다. 전용 Valkey·exporter는 RUN-0028 절차를 적용하되 profile만으로 broker 선택을 판정하지 않는다. 정지는 입력·예약을 차단하고 진행 실행을 대조한 뒤 하며, 암호화 키 변경은 RUN-0085와 일치하는 DB 복구 시점을 함께 승인한다.

## Procedure

### Execution Boundary

저장소 root에서 아래의 정확한 service/profile과 기존 container를 선택한다. 변경 전에 승인 대상, source/image, 선행 readiness, 필요한 운영 권한과 부작용 범위를 확인한다. `up`은 dependency/provisioning job을 만들 수 있고 profile은 격리가 아니다. 진단은 기존 container의 `exec`를 사용하고 단순 조회를 위해 client/provisioner를 띄우지 않는다. 재시작은 요청 중단·memory/queue 손실·부작용 반복을 일으킬 수 있으므로 대상 drain/backup 조건을 먼저 충족한다. `restart`는 바뀐 Compose 설정이나 교체된 secret bind를 불러오지 않는다.

Log를 보존하기 전에 payload·credential·header/cookie·private path를 제거하고 명령·시각·상태·제한된 시험 증거만 남긴다. 예상 밖 출력, backup 누락, dependency 실패나 승인되지 않은 부작용이면 중단하고 @buenhyden에게 넘긴다. Config rollback은 data/schema 복구가 아니다. 전체 기동·중지는 [cold-start Runbook](../01-common/0098-cold-start-and-reboot.md)의 대상 선택·의존성 확인 절차를 사용한다. 공통 절차는 [백업](../10-platform-and-backup/0021-backup-and-restore.md), [image 변경](../10-platform-and-backup/0086-dependency-version-management.md), [시크릿](../04-security-and-secrets/0085-openbao.md), [계정](../03-identity-and-access/0014-keycloak.md), [gateway·인증서](../02-gateway-and-networking/0013-traefik.md)가 소유한다. 대상이 실제 사용하는 자격 증명·상태에만 적용하며 secret 값은 증거로 요구하지 않는다.

### 선택형 공유 Valkey 계정과 Local Ollama

아래는 소스 선택·공개 설정 검증 절차다. 실제 Secret 생성·ACL 재기동·Queue 전환·
workflow 활성화는 별도 승인 창에서만 수행한다. 기존 기본 default/DB0는 유지하며,
전용 Valkey 선택도 profile만으로 바꾸지 않는다.

1. `SHARE_NAMED_USER`를 선택하면 Catalog `CACHE-027`의 원본
   `secrets/db/mng-valkey/n8n_password.txt`를 운영자가 안전하게 준비한다. 기존 비밀번호와
   다른 단일 링크 일반 파일이어야 하며 Valkey UID999와 secrets group이 읽을 수 있는
   소유권·0400/0600 또는 0440/0640 mode를 검증한다. 값은 출력하지 않는다.
2. Host `mng-valkey`, username `n8n`, Secret `mng_valkey_n8n_password`, DB `0`을 함께
   선택한다. `docker-compose.n8n-acl.yml`은 계정 생성·비밀 mount를 추가한다. 잘못된
   username/Secret/DB·누락 파일은 실패하며 shared default로 fallback하지 않는다.
3. 적용 전 schedule/webhook/new job을 차단하고 실행 중·지연·Retry 작업을 drain·대조한다.
   같은 DB0·prefix와 metadata/encryption key를 유지하고 Queue·AOF의 일관된 backup,
   빈 격리 복원·기존 default 복귀를 먼저 확인한다. `FLUSHDB`·임의 key 이관은 하지 않는다.
4. 정상 인증·Worker/Retry/Delayed·Runner와 다른 key/channel·DB·위험 command 거부,
   잘못된 비밀번호·회전·재기동·AOF 복원까지 exact image로 검증한다. 현재 소스/합성
   검사는 그 인수가 아니며 이 native/HOME 단계는 `NOT_RUN`이다.

공개 입력으로 선택 구성이 해석되는지만 확인한다(실제 값 파일을 읽지 않음):

```bash
N8N_VALKEY_USERNAME=n8n N8N_VALKEY_SECRET=mng_valkey_n8n_password \
  docker compose --env-file .env.example -f docker-compose.yml \
  -f infra/04-data/mng-db/docker-compose.n8n-acl.yml \
  --profile mng --profile workflow-n8n config --quiet
```

Ollama는 위 계정 선택과 독립이다. 승인된 Local Node의 실행자는 `n8n-worker`이며
다음 조합은 Worker와 Ollama에만 새 internal 망을 추가한다. Main/Code Runner에
추가 망을 주지 않으며 기존 edge/AI peer의 Ollama API 접근을 제거하지 않는다.

```bash
docker compose --env-file .env.example -f docker-compose.yml \
  -f infra/07-workflow/n8n/docker-compose.ollama-local.yml \
  --profile workflow-n8n --profile ollama config --quiet
```

실제 배포 전 각 overlay를 최종 명령에도 유지하고 필요한 profile·정확한 target과
자료·복구 Owner를 승인한다. 기존 Ollama Native Node에서 `http://ollama:11434`의
Credential를 값 없이 결속하고 Worker의 목록·생성·embedding·실패/복구를 확인한다.
추가 망·기존 edge/AI 망에 모두 속하지 않은 peer는 거부돼야 한다. Main만 성공하거나
Worker가 차단되면 FAIL이며 소스 render를 Native PASS로 바꾸지 않는다. Cloud는 별도
API Key·전송 데이터·비용 승인 전 `BLOCKED_CLOUD_APPROVAL`이고 로컬 cloud 차단은 유지한다.
rollback은 정확한 Worker/Ollama를 drain 후 overlay 없이 재생성하는 별도 승인 작업이다.
이전 source로 되돌리는 것만으로 실제 연결·queue 상태의 복구를 주장하지 않는다.

### 시나리오 1: 워커 노드 중단 (Worker Down)

1. 워커 로그 확인: `docker compose logs --tail=50 n8n-worker`. 출력에서 payload와 credential을 제거한 근거만 보존한다.
2. schedules/webhooks/inbound producers를 중지하고 실행/대기 작업, DB 백업과 외부 부작용을 조정한다. 재시작만으로 exactly-once 실행을 보장하지 않는다.
3. 선택한 broker host/secret pair에 대해 [Valkey Runbook](../05-databases-and-storage/0028-management-database.md)의 인증/queue 진단을 따른다. Profile이나 exporter health만으로 선택·준비 상태를 판정하지 않는다.
4. DB와 broker가 정상이고 재시작 영향이 승인되었을 때만 `docker compose restart n8n-worker`를 실행한다. 이후 worker 등록과 matching runner를 확인한다.

### 시나리오 2: 데이터베이스 연결 오류

1. DB 호스트(`POSTGRES_MNG_HOSTNAME`)가 가용한지 확인.
2. 시크릿 파일 경로/권한과 DB readiness를 값 출력 없이 확인한다: `docker compose exec n8n ls -l /run/secrets/n8n_db_password`. DB/권한 문제이면 중단하고 DB 소유자에게 넘긴다.
3. 실행 중 부작용 조정 후 승인된 경우에만 main을 재시작한다: `docker compose restart n8n`. Readiness와 worker/runner 등록을 다시 확인한다.

### 시나리오 3: Task Runner 오류

1. Task Runner 로그 확인: `docker compose logs n8n-task-runner n8n-task-runner-worker`
2. Core/runner 버전 불일치와 token/broker 연결부터 확인한다. 선언된 버전 정렬만으로 런타임 호환성을 수용하거나 재시작을 승인하지 않는다. 일치하는 버전·broker readiness·중단 영향이 확인된 경우에만 `docker compose restart n8n-task-runner n8n-task-runner-worker`를 실행한다.

### 격리 native 검증

이 절차는 검토된 source closure·합성 자산·고정 캐시 image만 사용하는 opt-in 시험입니다.
실제 HOME stack 기동 권한이나 검증 완료 표시는 아닙니다. 첫 전체 실행은 n8n main
readiness와 Airflow migration session role에서 각각 ERROR였습니다. 두 시험의 자동 cleanup
FAIL과 후속 정확한 대상 reconciliation PASS는 별도 기록입니다. 이후 n8n의 mount·alias·
user-folder를 맞춘 전체 실행도 main readiness에서 ERROR였고 migration 완료까지만
확인했으며 해당 실행의 cleanup은 PASS였습니다. Production entrypoint와 이미지 bytes는
바꾸지 않았습니다. Airflow 후속 실행도 8개 role 기동 뒤 scheduler migration 명령에서
ERROR였으며 내부 원인은 UNKNOWN입니다. 그 실행의 자동 cleanup FAIL과 exact
reconciliation PASS를 따로 보존합니다. 새 config source 수정은 과거 실패 원인의 증거가
아닙니다. 세 번째 Airflow 실행은 보호된 진단에서 metadata DB의 `airflow` 연결에
pg_hba 규칙이 없고 TLS가 사용되지 않았다는 FATAL을 확인했습니다. 자동 cleanup FAIL과
진단 후 exact reconciliation PASS를 보존하며 그 진단만으로 새 SCRAM 규칙의 통과를 입증하지는 않습니다.
현재 V6 실행은 앞선 pg_hba 오류 구간을 통과한 뒤 319.937초에 worker의 Python 호출에서 PutObject InternalError로
ERROR였습니다. 보호된 진단에서 botocore ClientError와 최대 재시도 1회를 확인했으나
Seaweed 내부 원인은 UNKNOWN이고 게시 수용은 입증되지 않았습니다. 모든 Docker
exact·pending·swept ID는 비었고 자동 cleanup FAIL은 private 진단 보존 때문입니다.
별도 parent reconciliation은 PASS이나 독립 zero 확인은 pending입니다. 원래 부분
FAIL과 capture identity 누락 한계를 보존하며 자동 cleanup FAIL을 고치지 않습니다.
workflow·worker 업무·SMTP·복원 성공 증거는 아닙니다. 최신 상태는
[Task0019](../../../03.specs/0204-service-integration-security-and-operations/tasks/tsk-0019-n8n-native-notification.md)와
[Task0020](../../../03.specs/0204-service-integration-security-and-operations/tasks/tsk-0020-airflow-native-publication.md)을 확인합니다.

1. 저장소 root에서 selector 없는 기본 시험으로 guard와 default skip을 확인합니다.
   이 명령은 Docker 실행을 선택하지 않습니다.

   ```bash
   env -i PATH=/usr/bin:/bin LANG=C.UTF-8 LC_ALL=C.UTF-8 PYTHONPATH="$PWD" \
     python3 -B -s -S -P -m unittest tests.validation.test_opsflow_native_boundaries \
     tests.validation.test_opsflow_native_rehearsal \
     tests.validation.test_opsflow_airflow_native_rehearsal \
     tests.validation.test_opsflow_native_evidence \
     tests.validation.test_opsflow_airflow_native_evidence -v
   ```

2. 실행할 commit과 source closure를 검토하고 아래 recipe의 `OPSFLOW_REVIEWED_SOURCE_SHA`에
   정확한 full SHA를 제공합니다. native 소스가 아직 미커밋이면 이 recipe는 HOLD입니다.
   Git/source 검증을 통과한 뒤에만 소스 상수에서 image ID를 읽습니다. mutable tag만으로
   대조하지 않습니다. PG·Valkey·runner·
   Mailpit·S3 등 fixture가 요구하는 모든 캐시도 각 guard의 정확한 ID와 맞아야 합니다.
   캐시 누락·다른 label·manifest/config·architecture·source hash면 HOLD하며 자동 pull하지 않습니다.

3. 두 fixture 공통의 `/tmp/hyhome-opsflow-native-rehearsal.lock`과 양쪽 attempt prefix의
   소유 자원을 확인합니다. stale container/network/attempt 디렉터리·미해결 cleanup이면
   중단합니다. lock을 지우거나 다른 소유자의 자원을 정리해 admission을 통과하지 않습니다.
   한 fixture의 cleanup과 lock 해제를 확인한 뒤 다음 fixture를 선택합니다.
   진단 증거를 의도적으로 보존한 attempt도 admission barrier이며, 살아 있는 Docker
   자원이 있다는 뜻으로 단정하지 않습니다. 아래 실패 분류와 정확한 대조를 먼저 완료합니다.
4. prestart MemAvailable 7GiB·`/tmp` staging 여유 10GiB·inode 10%와 새 압력 관측을 확인합니다.
   실행 전 2초 간격의 두 관측에서 memory PSI full avg10·avg60은 모두 0이고,
   그 구간의 oom_kill·pswpout 증가는 모두 0이어야
   합니다. full total microseconds는 기록만 하며 양의 total 차이 자체는 HOLD 조건이 아닙니다.
   SwapFree도 기록하되 별도 고정 하한은 적용하지 않습니다. fixture는 Docker 호출 전
   MemAvailable 3GiB를 검사합니다. coordinator의 압력 검사는 승인된 구간의 bounded
   pre/post 관측이며 연속 watchdog이 아닙니다. RAM guard나 전후 관측으로 호출 도중의
   압력·OOM 부재를 보장하지 않습니다. 관측 위반·누락은 HOLD입니다.
5. `OPSFLOW_NATIVE_FAMILY`를 `n8n` 또는 `airflow` 하나로 정합니다. 아래 표는 recipe가
   구성하는 정확한 child 선택자입니다. 두 fixture를 함께 선택하지 않습니다.

   | 구분 | child selector | 필수 환경 선택자 |
   | --- | --- | --- |
   | n8n | `tests.validation.test_opsflow_native_rehearsal.OpsflowN8nNativeRehearsal.test_actual_queue_runner_capture_unknown_reconcile_and_restore` | `OPSFLOW_N8N_NATIVE_REHEARSAL=1`, `OPSFLOW_N8N_NATIVE_IMAGE=$opsflow_image`, `OPSFLOW_N8N_NATIVE_CONTEXT=default` |
   | Airflow | `tests.validation.test_opsflow_airflow_native_rehearsal.AirflowNativeRehearsal.test_actual_celery_publication_retry_replay_and_empty_restore` | `OPSFLOW_AIRFLOW_NATIVE_IMAGE=$opsflow_image`, `OPSFLOW_AIRFLOW_NATIVE_CONTEXT=default` |

   관련 선택자가 전부 없으면 native skip입니다. 일부만 있거나 잘못된 image/context면
   실패해야 합니다. `DOCKER_HOST`, `DOCKER_CONTEXT`, `DOCKER_TLS_VERIFY`, `DOCKER_CERT_PATH`
   override를 전달하지 않습니다. 실제 image ID는 소스 상수에서 대입하며 위 표의 변수
   이름을 literal 값으로 넘기지 않습니다.
6. fixture별 cap은 아래와 같으며 임시 probe의 별도 peak를 승인 packet에 포함합니다.
   각 container의 memory-swap은 memory와 같고 PIDs·CPU·tmpfs를 제한합니다. read-only root,
   고정 non-root user, cap-drop ALL·no-new-privileges·내부 network를 확인합니다. n8n의
   secret-prep만 승인한 일회성 network-none root/CHOWN 작업 뒤 즉시 제거합니다.
   공개 port·운영 volume·실제 credential·외부 SMTP/업무 경로는 사용하지 않습니다.

   | fixture | steady role 합계 | 추가 작업 |
   | --- | --- | --- |
   | n8n | 7개, 3136MiB·1.60 CPU | secret-prep 32MiB·0.05 CPU, capture-probe 128MiB·0.10 CPU; 동시에 남지 않도록 확인 |
   | Airflow | 8개, 3648MiB·2 CPU | 사전 probe 512MiB·0.25 CPU; 전체 실행과 직렬 분리 |

7. GNU `timeout`, util-linux `prlimit`, Git·Python·Docker가 준비된 저장소 root에서 아래
   recipe를 실행합니다. 앞선 source·대상·fresh pressure 수용을 통과했을 때만 실행합니다.

### 독립 통지 실패와 fresh claim 복구

이 절차의 실제 outage·회전·복원 시험은 NOT_RUN입니다. 먼저 P05 Task에 정확한 workflow,
image·executor·DB/role·capture 대상·backup·빈 restore 대상·writer·cleanup·rollback을
정합니다. 대상이 없는 명령이나 운영 환경의 fault injection은 실행하지 않습니다.
SQL004를 적용한 실행 사본은 서버 UTC millisecond `lease_until`을 포함한 여섯 claim 필드를
소비합니다. Transport 생성과 send 직전에 SMTP 15초+ack 5초+시계 오차 5초보다 많은
시간이 남아야 합니다. 실제 DB/worker clock skew가 5초 이내이며 DB timeout/cancellation이
ack 예산에 맞는지 확인하기 전에는 활성화하지 않습니다. 이 검사는 분산 fencing이 아닙니다.

SMTP 응답 유실·node 호출 오류·ack false/유실은 unknown으로 격리하고 자동 재전송하지
않습니다. 구버전 retry 함수도 격리하며 실제 SMTP 시작 전 취소만
`retry_not_sent_notification`으로 제한합니다. DB 장애로 격리 기록이 실패하면 불확실한
sending을 유지하고 다음 claim에서 만료 상태를 unknown으로 바꿉니다. 오래된 SMTP node에서
재개하지 않습니다. Mailpit capture·run·Message-ID와 기존 수락/불확실 증거를 대조한 뒤
운영자가 먼저 정확한 workflow ID의 polling을 inactive로 바꾸고 새로운 manual 실행도
차단합니다. 해당 workflow를 실행할 수 있는 모든 main/manual executor와 queue worker의
기존 execution ID·in-flight SMTP 상태를 대조하고, drain 완료 또는 해당 실행 process의
확인된 종료를 영수증으로 보존해야 합니다. 멈춘 worker가 나중에 다시 전송할 수 있으면
`not_sent`로 재queue하지 않습니다. Mailpit에서 메시지가 보이지 않는 것만으로 no-send를
증명하지 않습니다. 전체 worker 중지는 다른 workflow를 끊으므로 승인된 운영 window와
정확한 container/execution 소유권 없이는 수행하지 않습니다. 현재 provider의 개별 실행
취소·worker 종료 경로를 확인할 수 없으면 named operator에게 넘기고 BLOCKED로 유지합니다.
이 조건을 만족한 뒤에만 migrator session에서 `SET ROLE opsflow_owner`하고
`reconcile_notification(id, 'accepted_by_smtp' 또는 'not_sent', evidence_sha256)`를
해당 한 건에만 적용합니다. 불확실하면 unknown을 유지합니다. Notifier에는 대조 권한이
없으며 다섯 번 상한에 도달한 no-send도 dead로 남습니다. 직접 outbox UPDATE·전체 reset은
사용하지 않습니다. Polling을 중지하고 outbox를 보존하는 것이 source rollback 경계입니다.
MNG metadata DB와 같은 encryption key·custom artifact·필요한 queue 상태를 함께 백업하고
schedules/egress를 차단한 빈 격리 대상에만 복원합니다. 복원 후 unknown/accepted 상태와
claim 결과를 먼저 확인합니다. Source revert만으로 schema나 cluster ACL을 되돌리지 않습니다.
공식 n8n UI/API credential 회전과 stale native 실행 사본 검증은 P04/P02 담당자와 조정합니다.

   값을 같은 권한의 새 파일로 만든 뒤 경로를 바꾸고, 다음 `dispatch`가 401 없이
   진행되는지 확인한 다음 Gateway 측 이전 값을 폐기하는 순서로 수행합니다. 값은
   인자·환경 변수·출력·작업 기록에 남기지 않습니다. 401·403 `failed` 기록은
   회전 후에도 자동으로 다시 열지 않습니다.
5. 복구 판단이 불가능하거나 검증기 경로·SHA가 다르면 중단하고 정제된 상태,
   해시, 시각과 확인한 범위를 @buenhyden에게 전달합니다. 원본과 Outbox를
   보존한 채 별도 운영 승인을 기다립니다. Source revert는 저장된 상태의 복구를
   뜻하지 않습니다.

#### 보호 설치

운영 Publisher는 Hermes 도구와 다른 전용 계정으로, 작업 사본이 아닌 root 소유
불변 release에서 `python3 -I`로 실행합니다. 인터프리터·import 경로·적재된 모듈·
`cryptography` 하위 파일·키 저장소 중 하나라도 root 소유가 아니거나 group·other
쓰기가 가능하거나 실행 계정이 쓸 수 있으면 신뢰 판정이 `blocked`를 돌려줍니다.
아래 단계는 각각 별도 승인 단위이며 아직 수행하지 않았습니다.

1. 계정(승인 단위: A 호스트 계정 생성): 로그인 셸 없는 시스템 계정
   `hermes-publisher`를 만들고 Hermes 계정과 그룹을 공유하지 않습니다. 복구는
   계정 삭제입니다.
2. 설치(승인 단위: `/opt/hermes-publisher` 생성): 설치기는 tar의 커밋 ID를
   검증할 수 없으므로 Hermes·Publisher 계정이 쓸 수 없는 root 소유 clone에서
   root로 실행합니다. 설치기는 root 전용이 아닌 tar나 prefix 상위 경로를 거부합니다.
   검토된 커밋으로
   `git archive --format=tar -o release.tar <commit> -- infra/07-workflow/n8n/workloads/hermes-blog-ingestion`을
   만들고 `sudo python3 -I install.py --archive release.tar --python /usr/bin/python3.12`를
   실행합니다. Ubuntu에서는 `python3.12-venv`가 필요합니다. 출력된 release 경로에서
   `sudo -u hermes-publisher <release>/venv/bin/python -I -m publisher.cli verify-install`이
   `{"keys": N, "runtime": "protected"}`인지 확인합니다. 복구는 실행기를 이전
   release로 돌리는 것이며 release와 Outbox를 지우지 않습니다.
3. 대기함·인증 파일(승인 단위: 전용 경로와 Secret 배치): 대기함 디렉터리 0700,
   인증 헤더 파일 0600을 전용 계정 소유로 둡니다. Hermes 계정은 읽을 수 없어야
   합니다.
4. 실행기(승인 단위: systemd 서비스·timer 등록): 전용 계정으로 `dispatch`를 주기
   실행합니다. n8n에는 재시도·예약 실행을 두지 않습니다.

#### 생산자 키 등록·회전·폐기

키 저장소는 `publisher/producer-keys.json`이며 공개키만 담습니다. 변경은 저장소
PR과 독립 검토로만 하고, 병합된 커밋을 새 release로 설치해야 반영됩니다.
서명 계약(`DOMAIN`, envelope, 키 항목 형식)의 정본은 `publisher/trust.py`입니다.

1. 등록: 제한 생산자 계정이 Hermes LLM 도구·내보내기와 다른 계정인지, 개인키가
   그 계정 밖에서 읽히지 않는지 보호 생성·보관 증거로 확인합니다. 원시 32바이트
   공개키의 SHA-256 지문을 생산자 계정에서 따로 받아 PR의 지문과 대조한 뒤
   공개키(base64)와 `key_id`, 허용 `jobs`, `not_before`, `not_after`를 추가합니다.
   개인키와 합성 시험 키는 저장소·Publisher에 들이지 않습니다. 등록 직후 해당
   작업의 서명된 실제 Companion 1건이 `dispatch` 전 신뢰 판정을 통과하는지 확인합니다.
2. 회전: 새 키를 겹치는 유효 기간으로 추가하고, 생산자가 새 키로 서명을 시작한
   것을 확인한 뒤 이전 키의 `not_after`를 앞당깁니다. 이미 대기함에 있는 기록은
   서명 키가 유효한 동안에만 전송되므로 이전 키로 서명된 `pending`·`uncertain`
   기록을 먼저 비웁니다. 신뢰 판정에 막힌 `sending`·`uncertain` 기록은 `dispatch`가
   `uncertain`으로 집계해 종료 코드 1로 드러냅니다.
3. 폐기: 개인키 노출이 의심되면 즉시 `revoked_at`을 추가해 병합합니다. 폐기는
   소급하므로 그 키로 서명된 미전송 기록은 요청 결속·전송·재전송 모두 막힙니다.
   이미 `delivered`인 기록은 Gateway에서 따로 검토합니다. 새 키로 다시 서명된
   Companion은 기존 서명을 바꿀 수 없으므로 새 실행으로 다시 만들어야 합니다.

6. Worker 연결(승인 단위: Worker 재생성): `n8n-worker`를 재생성해 `n8n_blog_ingest_net`에

    적용 직전에 다시 측정하고 같으면 `infra/01-gateway/traefik/dynamic/hermes-webhook.yml`을
    둡니다(2026-11-01 적용). 즉시 반영되며 복구는 파일 삭제입니다.
11. Export 진입(승인 단위: Traefik 재생성과 동적 구성 변경): Compose는 이미 Traefik을
    `blog_export_net`에 두므로 이 브랜치 병합 뒤의 어떤 Traefik 재생성도 모든 진입을
    잠깐 끊고 이 망에 붙습니다. 그 재생성 자체를 이 승인 단위로 다루고, 붙은 뒤 B의 출발지가 `192.168.0.22`로 보이는지와 A 서명자의
    출발지를 측정하고, 같으면 `dynamic/blog-export.yml`을 둡니다(2026-11-01 적용, B 출발지 측정은 Dry Run 때).
    `blog-export.hy.home.arpa`는 B와 A에서 `192.168.0.13`으로 해석되어야 합니다.
    다른 경로·메서드는 Traefik 404이고 Token 범위는 Gateway가 확인합니다. 복구는 파일
    삭제이며 Traefik의 빈 망 연결은 영향이 없습니다.
12. Windows Dry Run(승인 단위: 서버 B 수신기 설정): B에는 새 프로그램·WSL·Docker·수신
    서비스를 설치하지 않고 Vault도 옮기지 않습니다. Blog-data 같은 커밋의
    `scripts/ops/receive-hermes-exports.ps1`을 Windows PowerShell 5.1로 `-DryRun` 실행합니다.
    설정의 `base_url`은 `https://blog-export.hy.home.arpa`, CA 파일은 A의 mkcert 루트
    공개 인증서이며 `export_read`·`export_ack` Token 파일은 따로 둡니다. Dry Run은
    스테이징·Vault·영수증·ACK를 쓰지 않습니다.
13. 실제 수신 확인: Hermes Cron 결과가 201로 영속되고 같은 바이트 재전송이 200 중복인지,
    LAN 출발지·다른 경로·GET이 SSO나 403에 남는지 봅니다. 서명된 Evidence가 있는
    항목만 `attest-queue`로 `ready` Export가 되고, 직접 경로 보고서도 대기열에서 확인되며 원본이 맞지 않는 항목과 승인되지 않은 작업은
    `held`에 남습니다. 합성 보고서를 운영 Gateway에 보내지 않습니다.
14. Windows 수신·ACK: B 수신기를 실제로 실행해 Markdown 길이·SHA-256·UTF-8 검사와
    덮어쓰지 않는 설치 뒤 ACK 201을 확인합니다. Gateway의 `acknowledged`만 Windows 저장
    완료입니다. A의 수신 성공이나 n8n 성공을 B의 저장 완료로 기록하지 않습니다.
15. 운영 복구 확인: 3단계 백업 경로를 기존 백업 체계에 연결하는 일은 별도 승인입니다.
    Gateway·Worker·Traefik 재시작 뒤 같은 요청·Attestation·ACK의 재전송이 200 중복인지
    확인합니다. 복원 시험은 복제본으로만 합니다.

   `sudo python3 -I install.py --role attester --archive release.tar --python /usr/bin/python3.12`로
   Attester 전용 release(`/opt/hermes-attester/releases/<commit>`, 서명·원본 수집 모듈 포함)를
   설치합니다. Publisher release(`--role publisher`, 기본값)는 이 모듈을 싣지 않습니다.
   venv 생성에는 `python3.12-venv`가 필요합니다. `/opt/hermes-attester/current`를 그 release로 연결한 뒤
   `deploy/hermes-attester.{service,timer}`를 `/etc/systemd/system/`에 복사하고
   `systemctl daemon-reload` 후 `systemctl enable --now hermes-attester.timer`로 켭니다.
   런타임 Python은 표준 HTMLParser의 이차 입력(quadratic input) 보완이 들어간 패치 릴리스여야 하며, 정확한 최소 버전은 설치 시 CPython 보안 공지로 확인합니다. 먼저
   `attest-queue --help`와 한 번의 수동 실행(`systemctl start hermes-attester.service`)으로 개수 출력을 확인합니다. 복구는 timer 중지와
   `current` 링크 제거입니다.
8. 위가 모두 끝난 뒤에만 Hermes 플러그인·프롬프트(`source_quotes`)를 배포합니다.

Hermes 플러그인 설치본 확인(읽기 전용): 저장소 `hermes-plugin/`의 `__init__.py`,
`plugin.yaml`, `schemas.py`, `tools.py`와 Hermes 설치본
`~/.hermes/plugins/research-report/`의 같은 파일을 `sha256sum`으로 비교하고
`plugin.yaml`의 `version`을 함께 기록합니다. 다르면 설치본을 고치지 않고 Hermes
작업공간에 넘깁니다. 플러그인 설치·갱신은 Hermes 작업공간 소유입니다.

관측은 기존 체계만 씁니다. n8n 지표의 흐름 실행 결과, Traefik 라우터 지표의
`hermes-blog-ingestion-webhook`·`blog-export-*`·`blog-attestation` 상태 코드(401·403·
404·409·422·429·5xx), 컨테이너·디스크 지표, Gateway `/v1/summary`, Publisher `status`,
`attest-queue` 결과, 그리고 `export_read` 목록 조회의 `ready`·`held`·`conflict` 수와 가장
오래된 `ready`의 `created_at`, 마지막 `acknowledged`의 `updated_at`입니다. Gateway에는
지표 엔드포인트가 없어 Prometheus 수집과 경보 기준은 Blog-data 지표 계약과 운영 주기
확인 뒤 별도 승인으로 정합니다.
본문·비밀·보고서 ID는 지표 표지에 쓰지 않습니다. 실제 전달이 안정화된 뒤에만
A의 수집 경로와 분리된 별도 조회 경로·Token으로 n8n MCP Server Trigger의 조회 전용 `list_review_candidates`,
`get_ingestion_status`, `get_ingestion_summary`를 검토합니다. 각각 Gateway의
`GET /v1/candidates`, `GET /v1/ingestions/{id}`, `GET /v1/summary`를 사용합니다.
현재 Gateway에는 전문 검색 API가 없으므로 검색 도구를 제공하지 않습니다. 임의
HTTP 호출, capture·review·삭제 같은 쓰기, GitHub 쓰기는 포함하지 않습니다.

## Failure and Recovery

### Rollback or Recovery

- 이 Runbook에 기록된 복구·rollback 절차와 아래의 `Safe Rollback or Recovery Procedure` 하위 절차만 사용한다.
- 아래 HOME n8n metadata·data·encryption-key 격리 복원은 미실행 상태다. 별도 SQL fixture의 논리 복원과 구분하고 완료 전에 날짜가 있는 증거를 확인한다.
- 관찰한 장애가 문서화된 절차와 다르면 변경을 중지하고 증거를 보존한 뒤 아래 Escalation 절에 따라 보고한다.

#### Safe Rollback or Recovery Procedure

- [ ] 서비스를 재시작하기 전, 현재 실행/대기 중 workflow와 DB 백업 상태를 확인하십시오.
- [ ] 만약 `N8N_ENCRYPTION_KEY`가 변경되어 이전 데이터 복호화가 불가능한 경우, 이전 키로 롤백하거나 자격 증명을 재설정해야 합니다.

#### Planned isolated restore rehearsal

**Project 이름만 바꿔서는 실행할 수 없다.** Rehearsal 전에 고정 container name, host port, bind path, external network와 route 충돌을 제거하고 production 통지·workflow egress를 차단한 별도 Compose/storage 정의를 승인한다. 격리와 대상 backup 계약을 검토하기 전에는 NOT_RUN으로 유지한다. 임의 project에 production volume이나 credential을 연결하지 않는다.

상태: **계획됨·미실행**. n8n 복원 성공 증거는 없다.

1. 이미지 digest, 버전, profile·환경변수 이름, 워크플로·실행 건수, 활성 실행, broker 선택, 백업 checksum을 기록한다. 예약·webhook·입력 생산자를 차단하고 진행 중 실행을 완료시키거나 상태를 명시적으로 대조한다.
2. PostgreSQL 소유자에게 `n8n` DB의 일관된 백업을 요청한다. 정확히 일치하는 `n8n_encryption_key`, DB·runner secret 참조, 선택한 broker secret, `n8n-data`, task-runner 데이터, `custom/`, 설정된 바이너리 저장소를 보존한다. Valkey AOF를 워크플로 원본 백업으로 사용하지 않는다.
3. 경로와 외부 작업을 차단한 별도 Compose 프로젝트·네트워크에 복원한다. PostgreSQL을 먼저 복원하고 같은 암호화 키와 산출물을 복원한 뒤 일치하는 호스트·secret 쌍으로 broker 하나를 선택한다.
4. DB·broker를 기동하고 main의 readiness와 worker의 broker 상태를 확인한다. 각 runner는 버전을 일치시키고 해당 main·worker 의존성이 정상화된 뒤 기동한다. 스키마 시작, 값을 출력하지 않는 자격 증명 복호화, worker·runner 등록, 외부 효과가 없는 수동 워크플로, 격리 경로의 통제된 webhook을 확인한다.
5. 검증 실패 시 격리 프로젝트를 중지하고 로그·checksum을 보존한 뒤 변경하지 않은 백업으로 돌아간다. 운영 경로나 데이터 교체에는 별도 승인이 필요하다.

### Escalation

검증 실패, secret 노출 위험, 파괴적 변경 필요 또는 예상 절차와 다른 상태이면 중단하고 @buenhyden에게 넘긴다. 정제된 증거, 시도한 단계와 현재 rollback/recovery 상태를 함께 전달한다.

[Task0017](../../../03.specs/0204-service-integration-security-and-operations/tasks/tsk-0017-n8n-stable-source-preparation.md)의

Task0017 고정 입력의 production build와 실제 custom node loader는 ISOLATED PASS이며 dev recipe의

encryption key와 metadata/data/queue 백업을 독립 보관하고 빈 환경에서 복원합니다.
이미지 태그 복귀만으로 schema migration 복구를 판정하지 않습니다.

2026-10-20에는 위 조건에 따라 실행 중이던 HOME 버전의 백업(DB dump·data tar·SHA256SUMS)을 먼저 만들고,
그 사본을 빈 격리 DB에 복원해 선언 버전의 마이그레이션·credential 복호화·queue worker와 external
runner의 JS/Python Code 노드를 확인한 뒤 HOME을 선언 버전으로 재생성했습니다. 기록과 남은 범위(SMTP,
HOME workflow 실행, HOME 복원)는 Task0017이 소유합니다. 되돌릴 때는 이미지 태그가 아니라 그
백업을 빈 DB에 복원합니다.
