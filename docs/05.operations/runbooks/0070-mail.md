# Stalwart Mail Runbook

## Overview

## Trigger and Preconditions

### Overview

### Trigger and Preconditions

### When to Use

listener/auth/TLS/DNS/queue failure, mailbox/config recovery, 또는 승인된
upgrade에 사용한다. 루트에서 작업하며 synthetic mail만 사용한다.

### 작업 선택과 복구 전제

변경 전에 정확한 서비스·데이터 경로·승인자·중단 영향을 기록하고 [공통 복구 전제](0021-backup-and-restore.md)를
적용한다. 격리 대상, 복구본 식별자·무결성, 여유 공간, 비밀 보관, 작성자 정지와
승격 승인 중 하나라도 불명확하면 중단한다. config·secret 교체는
[공통 수명주기 정책](../policies/0006-infrastructure-optimization-governance.md)의
단일 파일 bind 재생성과 비밀 비노출 확인을 따른다. 재시작은 데이터 복원이나 자격 증명
폐기 검증을 대신하지 않는다.

## Procedure

### Procedure

1. bounded state를 validate하고 캡처한다.

   ```bash
   docker compose --profile mail-server config --quiet
   docker compose --profile mail-server ps stalwart
   docker compose --profile mail-server logs --tail=200 stalwart
   ```

2. management UI, SMTP/submission, IMAPS, 설정 증상을 구분한다. listener 차이는
   미적용·부분 적용·수동 변경 모두에서 생길 수 있으므로 단일 원인으로 단정하지 않는다.
   plan을 다시 적용하지 말고 현재/의도 listener 식별자와 이전 복구본을 먼저 확인한다.
   승인된 합성 relay 시도는 SMTP `550`과 `Relay not allowed`로 거부되어야 한다.
   주소·제목·본문·token·credential은 근거에서 제외한다.
3. listener certificate/SNI, auth와 relay policy, DNS record, disk, 실제 설정된
   storage backend를 확인한다. SMTP socket을 safe relay로 취급하지 않는다.
4. storage/listener 점검 후 Stalwart만 재시작한다. 외부 전달 전에 relay denial과
   승인된 synthetic submission/retrieval 하나를 확인한다.

### Backup and isolated restore

1. data/blob/search/in-memory backend와 configuration/certificate/DKIM custody를
   inventory한다. 새 submission을 차단하고 queue를 drain하거나 기록한다.
2. 지원되면 실행 중인 version의 문서화된 CLI snapshot/export를 management object에
   사용하고, 각 backend의 consistent backup을 사용한다. local-only storage에
   online snapshot이 없으면 Stalwart를 중지하고 `/var/lib/stalwart` 전체를
   복사한다 (현재 선언 버전의 export 명령·일관성 계약을 확인하기 전에는 임의의 export 명령을 실행하지 않는다).
3. outbound SMTP가 차단된 isolated storage와 non-delivery hostname/network로
   복원한다. replacement credential과 certificate를 제공한다.
4. 설정·계정·mailbox 개수, 합성 IMAP 조회, 인증·relay 거부와 queue 상태를 확인한다. DNS와 owner 검토 후에만 delivery를 활성화한다.

### Upgrade

위 backup을 확보하고, release/storage/license note를 검토하고, 복원된 data에서
target image를 테스트하고, 사용 중인 모든 listener를 점검한다. 비호환 시 target을
중지하고 이전 image와 pre-upgrade data를 함께 복원한다.

### 최초 기동의 적용 전 확인

아래 최초 기동 순서는 새 저장소·승인된 도메인·이전 데이터 부재를 확인한 경우에만
적용한다. 기존 경로를 비우거나 Docker가 적절한 소유권을 자동 설정한다고 가정하지
않는다. helper 적용 전에 plan 전체의 생성·patch·삭제 목록을 승인받고 서버 health와
복구본을 확인한다. 서버가 준비되지 않으면 helper를 실행하지 않는다.

### 승인된 최초 기동

1. `${DEFAULT_COMMUNICATION_DIR}/stalwart/data`를 비어 있는 상태로 생성한다.
   승인된 기동 전에 정확한 새 경로의 소유권·권한이 선언된 이미지 사용자 요구사항과
   일치하는지 확인한다. 자동 소유권 보정을 가정하거나 기존 경로를 넓게 변경하지 않는다.
2. `docker compose --profile mail-server up -d stalwart`를 실행한 다음
   `docker compose --profile mail-server run --rm --no-deps stalwart-config`, 그다음
   `docker compose --profile mail-server restart stalwart`를 실행한다.
3. admin UI나 추가 plan을 통해 계정을 생성한다. 합성 메일을 사용하고 본문이나
   credential을 증거에 절대 기록하지 않는다.
4. 외부 배달에는 새로 승인된 요구 사항(DNS, SPF, DKIM, DMARC, 평판)과 릴레이
   규칙에 대한 검토된 변경이 필요하다.

### 보존 대상과 변경 검토

가능하면 버전이 지원하는 Stalwart CLI 스냅샷/export를 설정 객체에 사용하고,
설정된 각 데이터/blob/검색 백엔드에는 네이티브 백업 방법을 사용한다. 배포가
로컬 bind 기반 저장소만 사용하고 온라인 일관성 export가 없다면, Stalwart를
중지하고 메타데이터와 함께 `/var/lib/stalwart` 트리 전체를 복사한다
(현재 선언 버전의 export 명령·일관성 계약을 확인하기 전에는 임의의 export 명령을 실행하지 않는다). 인증서/개인 키 보관과 DNS/DKIM
레코드는 별도로 보존한다. outbound SMTP를 차단한 격리된 호스트 이름에서
복원하고, 계정/mailbox 수와 합성 조회를 검증한 다음 전환을 승인한다.

업그레이드 전에는 그 백업을 확보하고 테스트하며, release/스토리지/라이선스
노트를 읽고, 호환 이미지를 pin하고, 모든 listener를 검증한다. 이 문서 작업에서는
배달, 백업, 복원, 업그레이드를 실행하지 않았다.

### Listener 변경과 관리자 회전

저장소 루트에서 서버의 준비 상태, 적용할 plan 해시, 삭제될 listener 목록, 이전
plan과 datastore 복구본, 중단 영향 및 승인을 확인한다. `stalwart-config`는 서버
health를 기다리는 일회성 변경 작업이며 자체 HTTP health는 없다. 승인된 적용은
`docker compose --profile mail-server run --rm --no-deps stalwart-config`로
정확히 선택한다. 오류가 나면 재시도·재시작을 멈추고 부분 적용 범위를 확인한다.
성공 후 승인된 서버 재시작과 listener·인증·relay 검증을 거친다. 이전 plan 재적용도
삭제·patch를 일으키므로 자동 롤백으로 취급하지 않는다.

관리자 secret 교체는 [공통 수명주기 정책](../policies/0006-infrastructure-optimization-governance.md)을
따라 단일 파일 bind의 재생성 필요성을 확인한다. 승인된 `stalwart` 재생성 후 새
관리자 인증 성공과 이전 인증 거부를 값 노출 없이 확인한다. helper는 다음 승인된
실행 때 새 secret을 사용한다. 기존 이미지 복원은 datastore 변경을 되돌리지 않는다.

## Verification

### Evidence

종료 코드·listener/TLS/DNS 판정·backend 종류·백업 ID/checksum·개수·합성 test ID·
release/source 커밋과 최종 상태만 기록한다.

## Rollback and Escalation

### Rollback or Recovery

backup/restore, delivery, upgrade rehearsal은 **계획되었으나 미실행** 상태이다.
live unknown database를 복사하거나 rehearsal 중 outbound delivery를 활성화하지
않는다.

### Escalation

책임자는 `@buenhyden`이다. 아래 중단 조건과 영향받은 서비스·대상 소유자를 함께 기록하고, 추가 변경 없이 보고한다.

open-relay 동작, 알 수 없는 backend, backup/key custody 누락, test 중 실제 mail,
DNS/reputation 문제, 비호환 schema/license 동작이 있으면 중단한다.
