# k6 Load Test Recovery Runbook

## Overview

승인된 isolated k6 실행이 잘못된 endpoint를 대상으로 하거나 한도를 넘거나 비정상 종료할 때
부하를 멈추고 정리하는 절차다. root Compose의 `k6`는 `version`만 실행하므로 이 절차의
대상이 아니다.

## Trigger and Preconditions

승인된 isolated k6 test를 준비할 때, 또는 executor가 잘못된 endpoint를 대상으로
시도하거나, 합의된 limit을 초과하거나, finalization이 실패하거나, 예기치 않게 종료될
때 이 절차를 사용한다. root Compose의 `k6`는 `version`만 실행하며 이 런북의 traffic
명령 대상이 아니다.

## Procedure

### 승인된 격리 실행 준비

target owner가 target, traffic ceiling, stop condition, manifest, scenario revision,
Docker context, dedicated internal network와 WireMock peer identity를 승인한다. root
Compose를 `up`하거나 `k6` command를 override하여 실행하지 않는다. runner command와
실행 전 network/peer provisioning은 current Task의 별도 승인된 synthetic procedure를
따른다. runner는 다음 interface만 허용한다.

```bash
# doc-paths: illustrative
python3 infra/11-quality/k6/quality_run.py run \
  --manifest <approved-manifest.json> \
  --scenario-root <approved-scenario-directory> \
  --attempt-dir <new-empty-attempt-directory> \
  --docker-context <approved-docker-context> \
  --network <dedicated-internal-network> \
  --wiremock-container <approved-wiremock-container> \
  --guard-config <approved-guard-config.json> \
  --backend-network <approved-backend-network> \
  --backend-container <approved-wiremock-backend> \
  --metrics-egress-network quality_otlp_net \
  --relay-image grafana/alloy@sha256:<approved-digest> \
  --relay-token-file <absolute-path-to-quality_otlp_token.txt>
```

마지막 세 option은 manifest v2 `telemetry.mode=otlp`일 때만 함께 준다. controller가
attempt마다 `hyhome-k6relay-<run>-a<attempt>` relay를 만들고, 준비되면 k6를 실행하고,
끝나면 relay를 SIGTERM으로 비운 뒤 지운다. token 파일은 소유자 외에는 읽을 수 없어야 한다.
이미 만든 relay를 쓰려면 `--metrics-ingress-container`를 주며, 이때도 executor가 이름·label·
image·mount·설정 hash·network를 모두 검사한다.

실행 중 `Ctrl-C`나 SIGTERM을 보내면 executor가 `interrupted/runner_cancelled`(종료 코드
130)를 기록하고 그 attempt의 runner와 relay만 지운다. controller가 비정상 종료해 container가
남았으면 그 run만 정리한다.

```bash
# doc-paths: illustrative
python3 infra/11-quality/k6/quality_run.py cleanup --run-id <run-uuid> --docker-context <context>
```

manifest의 Docker network는 local bridge, `Internal=true`, `Attachable=false`이고
`hyhome.quality.run_id`, `hyhome.quality.purpose=k6-wiremock` label 및 manifest와 정확히
같은 subnet을 가져야 한다. 연결 peer는 하나뿐이며 running WireMock의 run ID·role·mock
mode label, `wiremock` alias, 단일 network, 비공개 port와 `extra_hosts` 없음이 일치해야
한다. executor는 digest image를 pull 없이, read-only root/scenario snapshot, 별도 summary
file, host UID/GID, CPU·memory·PID 상한, redirect 0으로 준비한다. `--guard-config`가 없으면
`/__admin` 우회를 막을 수 없으므로 executor는
`interrupted/path_confinement_unavailable` exit metadata만 남기고 container를 시작하지
않는다. guard config가 있어도 live target traffic 승인은 `BLOCKED`이므로 이 command를
live traffic 실행 증거로 사용하지 않는다.

### Recovery

1. 새 load를 먼저 중지한다. 승인 receipt의 정확한 executor container identity와
   dedicated network identity를 확인한 뒤, 해당 isolated container만 중지한다. root
   `k6` service, HOME service, 공유 network, volume을 중지하거나 제거하지 않는다.

2. target-side latency, error, saturation signal로 target 회복을 확인한다. impact가
   설명되지 않은 상태에서는 재시작하지 않는다.
3. sanitized job evidence를 캡처한다.

   target, manifest identity, scenario hash, image declaration, start/stop 시각, exit
   code, final state, exact cleanup receipt와 target 회복 여부만 기록한다. credential,
   raw stdout/stderr, response body, header, cookie, URL query는 기록하지 않는다.
4. metric이 없다고 scenario를 변경하지 않는다. root remote-write declaration은
   isolated executor가 소비하지 않는다. manifest v2 `telemetry.mode=otlp` run은
   `metrics-ingress` relay와 HOME Alloy 4319를 거친다. Alloy가 `quality_otlp_net`에
   있는지, Prometheus에 `instance=<run_id>-a<attempt>` series가 있는지, 그 `k6_http_reqs_total`
   합계가 k6 summary의 요청 수와 같은지 확인하기 전까지 전달 상태는 `NOT_RUN`이다.
5. scenario나 image 변경이 실패 원인이면 마지막으로 검토된 Git version으로 복원하고
   static check를 실행한 뒤, 실제 test 재실행 승인을 받기 전에 disposable low-load
   target을 사용한다.

### Backup and Recovery Status

영구적인 executor-container restore는 없다. Git으로 관리한 시나리오는 해당
revision에서 복원하고, 외부 프로젝트가 소유한 시나리오는 그 저장소의 검토본에서
복원한다. isolated executor가 remote write를 하지 않으므로 Prometheus backup을
이 실행 결과의 복구 근거로 사용하지 않는다.

### 시나리오 보존과 업그레이드

서비스 자체는 폐기할 수 있다. scenario snapshot, immutable attempt artifact와
finalization 결과를 보존하고, raw evidence가 검역되면 import하지 않는다. Image
upgrade 전에 k6 release note를 검토하고, 별도 승인된 isolated synthetic canary를
실행한다. Result semantics가 바뀌면 image pin, runner와 scenario를 함께 rollback한다.

## Verification

승인·대상·manifest identity·scenario hash·이미지 선언·시각·종료 코드·정제된 final
state·cleanup receipt와 대상 회복을 기록한다. credential, raw logs, request/response
body, cookie, Authorization, URL query는 절대 캡처하지 않는다.

### Static checks

```bash
bash scripts/hardening/check-all-hardening.sh 11-quality
HYHOME_COMPOSE_PROFILES=testing bash scripts/validation/validate-docker-compose.sh
```

live target 실행은 승인되지 않았으므로 HOME stop/cleanup은 `NOT_RUN`이다. live 실행이
승인된 후에는 정확한 isolated container가 중지·제거되고 target signal이
합의된 범위로 돌아오며 final evidence와 cleanup receipt가 보존될 때만 recovery가
완료된 것이다. Prometheus delivery는 별도 승인된 전달 검증 없이는 완료 조건이 아니다.

## Rollback and Escalation

### Rollback or Recovery

정확한 isolated executor만 중지하고, 마지막으로 검토된 scenario revision과 runner
source를 복원한다. 수신 측 Prometheus 절차로 이 실행 결과를 복구한다고 주장하지
않는다. 원래 target에 대한 승인을 받기 전에는 disposable synthetic target에만
재실행한다.

### Escalation

책임자는 `@buenhyden`이다. 아래 중단 조건과 영향받은 서비스·대상 소유자를 함께 기록하고, 추가 변경 없이 보고한다.

executor를 중지할 수 없거나, 중지 후에도 traffic이 계속되거나, target signal이
회복되지 않거나, credential 또는 raw log가 노출되었을 수 있거나, dedicated network
identity를 증명할 수 없을 때 escalation한다.
