# dbt Recovery Runbook

## Overview

## Trigger and Preconditions

### Overview

### Trigger and Preconditions

### When to Use

프로비저닝 실패, 연결 또는 권한 오류, 잘못된 모델 실행, 크리덴셜 교체 시
사용한다.

### Execution and stop boundary

대상: `dbt`, `dbt-db-provision`. 운영 checkout의 repository root와 승인된 Docker context를 확인한다. static source 점검만 승인된 경우 모든 runtime command는 NOT_RUN이다. raw log, rendered Compose, SQL/문서/벡터 payload, credential URI는 evidence에 붙이지 않고 결과·시간·target·source revision·종료 코드만 요약한다.

기동/정지는 [GDE-0099](../guides/0099-system-operations.md#selection-and-readiness)와 [POL-0006](../policies/0006-infrastructure-optimization-governance.md#source-and-lifecycle-boundary)의 consumer 영향·graceful shutdown 계약을 적용한다. 아래 재기동 예시는 정확한 daemon과 의존성 정상 상태를 owner가 승인했을 때만 사용한다. init/key-generator/provisioning job은 DDL·cluster identity·bucket policy를 변경하므로 routine restart 대상에서 제외한다. `--no-deps`는 이미 준비된 dependency를 유지할 때만 쓰며 최초 provisioning을 대신하지 않는다.

Upgrade/config 변경은 declared image/build/entrypoint와 mount를 비교하고 release 호환성·보존된 recovery point를 승인받은 뒤 대상만 적용한다. Git/image rollback은 schema/data/credential rollback이 아니다. 예상 health와 실제 사용자 기능이 다르거나 data/backup/ownership/credential이 불명확하면 중단하고 @buenhyden에게 scope·실패 신호·다음 검토를 전달한다. 실패한 복원 target과 증거는 보존하며 cleanup은 원래 기록한 identity를 확인한 소유 artifact만 별도 승인한다. 새로운 restore executor·client·network를 즉석에서 만들지 않는다.

## Procedure

### Procedure

1. dev-pg와 platform/feature provisioning이 이미 완료된 승인 환경에서 점검한다. 미완료라면 중단하고 named provisioning 승인을 받는다.

   ```bash
   docker compose --profile analytics-engineering config --quiet
   docker compose --profile analytics-engineering logs --tail=100 dbt-db-provision
   docker compose --profile analytics-engineering run --rm --no-deps dbt debug
   ```

2. 프로비저닝 `64` 종료는 명시적 입력 검사 또는 연결 대기 timeout이며 해당 runner의 DDL 전 실패다. 파일/shell 오류는 다른 코드일 수 있다. `3` 종료는
   거부 사유를 명시한다. 대상 데이터베이스 없음(`dev-platform-provision`을 먼저 실행),
   소스 소유자나 스키마 없음, 다른 역할이 소유한 대상 스키마, 대상이 소스와
   동일함 등이다.
3. 역할이 생성된 이후의 실패는 역할과 `CONNECT` 부여를 그대로 남긴다.
   `ON_ERROR_STOP`은 이를 되돌리지 않는다. 원인을 수정하고
   승인된 동일 scope의 `dbt-db-provision`만 재실행한다. role/grant 잔존을 먼저 확인하며 실패를 자동 rollback으로 해석하지 않는다.
4. 잘못된 모델 실행의 경우 `run --rm --no-deps dbt build --select <model>`로 영향받은
   relation을 다시 빌드한다. 증분 상태가 잘못된 것이 확실할 때만
   `--full-refresh`를 사용한다.

### Credential rotation

등록된 워크플로로 `secrets/db/dev-pg/dbt_password.txt`를 교체하고,
`dbt-db-provision`을 재실행한 뒤 `dbt debug`를 실행한다.

## Verification

### Evidence

종료 코드, 선택한 모델, relation 개수, 소스 커밋을 기록한다. 데이터 값이나
비밀번호는 기록하지 않는다.

## Rollback and Escalation

### Rollback or Recovery

`DBT_SCHEMA`의 각 relation마다 보존 범위와 source revision을 기록한다.
현재 tracked smoke view는 재생 가능하다. 추가 모델·incremental/history의 원본과 재생 가능성은 별도 검증하며 namespace만 보고 모든 relation을 disposable로 취급하지 않는다. 스키마를 삭제하는 것은 승인이 필요한 데이터
변경이다.

### Escalation

superuser 요청, 소스 스키마 쓰기 권한, 데이터베이스에 대한 `CREATE` 요청이
있으면 중단한다.
