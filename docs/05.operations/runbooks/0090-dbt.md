# dbt Recovery Runbook

## When to Use

프로비저닝 실패, 연결 또는 권한 오류, 잘못된 모델 실행, 크리덴셜 교체 시
사용한다.

## Procedure

1. 점검한다.

   ```bash
   docker compose --profile core --profile analytics-engineering config --quiet
   docker compose --profile core --profile analytics-engineering logs --tail=100 dbt-db-provision
   docker compose --profile core --profile analytics-engineering run --rm dbt debug
   ```

2. 프로비저닝 `64` 종료는 아무 변경도 일어나기 전의 입력 문제다. `3` 종료는
   거부 사유를 명시한다. 대상 데이터베이스 없음(`mng-pg-init`을 먼저 실행),
   소스 소유자나 스키마 없음, 다른 역할이 소유한 대상 스키마, 대상이 소스와
   동일함 등이다.
3. 역할이 생성된 이후의 실패는 역할과 `CONNECT` 부여를 그대로 남긴다.
   `ON_ERROR_STOP`은 이를 되돌리지 않는다. 원인을 수정하고
   `dbt-db-provision`을 재실행한다. 이 작업은 수렴한다.
4. 잘못된 모델 실행의 경우 `run --rm dbt build --select <model>`로 영향받은
   relation을 다시 빌드한다. 증분 상태가 잘못된 것이 확실할 때만
   `--full-refresh`를 사용한다.

### Credential rotation

등록된 워크플로로 `secrets/db/postgres/dbt_password.txt`를 교체하고,
`dbt-db-provision`을 재실행한 뒤 `dbt debug`를 실행한다.

## Evidence

종료 코드, 선택한 모델, relation 개수, 소스 커밋을 기록한다. 데이터 값이나
비밀번호는 기록하지 않는다.

## Rollback or Recovery

`DBT_SCHEMA`의 relation은 파생된 것이며 소스로부터 재빌드할 수 있다. 그중
원본 데이터는 하나도 없다. 스키마를 삭제하는 것은 승인이 필요한 데이터
변경이다.

## Escalation

superuser 요청, 소스 스키마 쓰기 권한, 데이터베이스에 대한 `CREATE` 요청이
있으면 중단한다.
