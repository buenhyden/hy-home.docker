#### Trigger and Scope

##### Trigger

이 런북은 Stalwart의 listener, 인증, TLS, DNS, queue 장애 진단과 메일박스·설정 복구, 승인된 최초 기동과 업그레이드 절차를 정의한다. 작업은 저장소 루트에서 하고 합성 메일만 사용한다.

listener/auth/TLS/DNS/queue failure, mailbox/config recovery, 또는 승인된
upgrade에 사용한다.

#### Preflight

##### Authority

변경 전 정확한 서비스·데이터 경로·승인자·중단 영향을 기록한다. 최초 기동 전에는 plan 전체의 생성·patch·삭제 목록을, Listener 변경 전에는 적용할 plan 해시·삭제될 listener 목록·중단 영향 및 승인을 확인한다.

##### Environment

루트에서 작업하며 synthetic mail만 사용한다.

###### 작업 선택과 복구 전제
<!-- core-payload-level:4 -->

변경 전에 정확한 서비스·데이터 경로·승인자·중단 영향을 기록하고 [공통 복구 전제](../10.platform-and-backup/0021-backup-and-restore.md)를
적용한다. 격리 대상, 복구본 식별자·무결성, 여유 공간, 비밀 보관, 작성자 정지와
승격 승인 중 하나라도 불명확하면 중단한다. config·secret 교체는
[공통 수명주기 정책](../../02.policies/01.common/0006-infrastructure-optimization-governance.md)의
단일 파일 bind 재생성과 비밀 비노출 확인을 따른다. 재시작은 데이터 복원이나 자격 증명
폐기 검증을 대신하지 않는다.

#### Procedure

##### Steps

| Step | Action | Expected Result | On Failure |
| --- | --- | --- | --- |
| 1 | `config --quiet` 검증, `lab.py status`, `stalwart` 로그로 bounded state 캡처 | 문서에 기록 없음 | 중단하고 Stop Conditions에 따라 escalation |
| 2 | management UI, SMTP/submission, IMAPS, 설정 증상 구분 (plan을 다시 적용하지 않음) | 승인된 합성 relay 시도가 SMTP `550`과 `Relay not allowed`로 거부됨 | open-relay 동작이면 중단 |
| 3 | listener certificate/SNI, auth/relay policy, DNS record, disk, storage backend 확인 | 문서에 기록 없음 | 알 수 없는 backend 또는 DNS/reputation 문제면 중단 |
| 4 | Stalwart만 재시작하고 relay denial과 승인된 synthetic submission/retrieval 하나 확인 | relay denial과 synthetic submission/retrieval 하나가 확인됨 | 중단하고 Stop Conditions에 따라 escalation |
| 5 | Backup and isolated restore: data/blob/search/in-memory backend와 config/certificate/DKIM custody inventory, 새 submission 차단 및 queue drain/기록 | 문서에 기록 없음 | backup/key custody 누락이면 중단 |
| 6 | Backup and isolated restore: 문서화된 CLI snapshot/export 또는 backend별 consistent backup, 없으면 Stalwart 중지 후 `/var/lib/stalwart` 전체 복사 | 문서에 기록 없음 | 현재 선언 버전의 export 계약을 확인하기 전에는 임의의 export 명령을 실행하지 않음 |
| 7 | Backup and isolated restore: outbound SMTP가 차단된 isolated storage와 non-delivery hostname/network로 복원 (replacement credential/certificate 제공) | 문서에 기록 없음 | test 중 실제 mail이 나가면 중단 |
| 8 | Backup and isolated restore: 설정/계정/mailbox 개수, 합성 IMAP 조회, 인증/relay 거부, queue 상태 확인 | 개수, 합성 IMAP 조회, 인증/relay 거부, queue 상태가 확인됨 | DNS와 owner 검토 전에는 delivery를 활성화하지 않음 |
| 9 | Upgrade: backup 확보, release/storage/license note 검토, 복원 data에서 target image 테스트, 모든 listener 점검 | 문서에 기록 없음 | 비호환 시 target을 중지하고 이전 image와 pre-upgrade data를 함께 복원 |
| 10 | 승인된 최초 기동: `${LAB_DATA_DIR}/stalwart/data`를 빈 상태로 생성하고 소유권/권한 확인 | 새 경로의 소유권/권한이 선언된 이미지 사용자 요구사항과 일치 | 자동 소유권 보정을 가정하지 않으며 기존 경로를 넓게 변경하지 않음 |
| 11 | 승인된 최초 기동: `lab.py up stalwart`로 lease 기동 후 `stalwart-config` 실행, `stalwart` restart | 문서에 기록 없음 | 서버가 준비되지 않으면 helper를 실행하지 않음 |
| 12 | 승인된 최초 기동: admin UI나 추가 plan으로 합성 메일 계정 생성 | 문서에 기록 없음 | 본문이나 credential은 증거에 기록하지 않음 |
| 13 | 승인된 최초 기동: 외부 배달은 새로 승인된 요구 사항(DNS, SPF, DKIM, DMARC, 평판)과 relay 규칙 변경 검토 후에만 진행 | 문서에 기록 없음 | DNS/reputation 문제면 중단 |
| 14 | Listener 변경: plan 해시, 삭제될 listener 목록, 이전 plan/datastore 복구본, 영향, 승인 확인 후 승인된 `stalwart-config` 적용 | 성공 후 listener/인증/relay 검증 통과 | 오류 시 재시도/재시작을 멈추고 부분 적용 범위 확인 (이전 plan 재적용은 자동 롤백이 아님) |
| 15 | 관리자 secret 교체: 단일 파일 bind 재생성 필요성 확인 후 승인된 `stalwart` 재생성 | 새 관리자 인증 성공과 이전 인증 거부 (값 노출 없이 확인) | 기존 이미지 복원은 datastore 변경을 되돌리지 않음 |

1. bounded state를 validate하고 캡처한다.

   - `docker compose --env-file labs/.env -f labs/stalwart/docker-compose.yml --profile mail-server config --quiet`
   - `python3 scripts/operations/lab.py status`
   - `docker compose --env-file labs/.env -f labs/stalwart/docker-compose.yml --profile mail-server logs --tail=200 stalwart`

   첫 명령만 render-only다. 기동·재시작·정지는 `python3 scripts/operations/lab.py check|up|down stalwart`
   lease 규칙을 따른다. HOME container는 이 LAB에 제출할 수 없으므로 HOME 앱 메일 증상은
   Mailpit 런북으로 보낸다.

2. management UI, SMTP/submission, IMAPS, 설정 증상을 구분한다. listener 차이는
   미적용·부분 적용·수동 변경 모두에서 생길 수 있으므로 단일 원인으로 단정하지 않는다.
   plan을 다시 적용하지 말고 현재/의도 listener 식별자와 이전 복구본을 먼저 확인한다.
   승인된 합성 relay 시도는 SMTP `550`과 `Relay not allowed`로 거부되어야 한다.
   주소·제목·본문·token·credential은 근거에서 제외한다.
3. listener certificate/SNI, auth와 relay policy, DNS record, disk, 실제 설정된
   storage backend를 확인한다. SMTP socket을 safe relay로 취급하지 않는다.
4. storage/listener 점검 후 Stalwart만 재시작한다. 외부 전달 전에 relay denial과
   승인된 synthetic submission/retrieval 하나를 확인한다.

###### Backup and isolated restore
<!-- core-payload-level:4 -->

1. data/blob/search/in-memory backend와 configuration/certificate/DKIM custody를
   inventory한다. 새 submission을 차단하고 queue를 drain하거나 기록한다.
2. 지원되면 실행 중인 version의 문서화된 CLI snapshot/export를 management object에
   사용하고, 각 backend의 consistent backup을 사용한다. local-only storage에
   online snapshot이 없으면 Stalwart를 중지하고 `/var/lib/stalwart` 전체를
   복사한다 (현재 선언 버전의 export 명령·일관성 계약을 확인하기 전에는 임의의 export 명령을 실행하지 않는다).
3. outbound SMTP가 차단된 isolated storage와 non-delivery hostname/network로
   복원한다. replacement credential과 certificate를 제공한다.
4. 설정·계정·mailbox 개수, 합성 IMAP 조회, 인증·relay 거부와 queue 상태를 확인한다. DNS와 owner 검토 후에만 delivery를 활성화한다.

###### Upgrade
<!-- core-payload-level:4 -->

위 backup을 확보하고, release/storage/license note를 검토하고, 복원된 data에서
target image를 테스트하고, 사용 중인 모든 listener를 점검한다. 비호환 시 target을
중지하고 이전 image와 pre-upgrade data를 함께 복원한다.

###### 승인된 최초 기동
<!-- core-payload-level:4 -->

아래 순서는 새 저장소·승인된 도메인·이전 데이터 부재를 확인한 경우에만
적용한다. 기존 경로를 비우거나 Docker가 적절한 소유권을 자동 설정한다고 가정하지
않는다. helper 적용 전에 plan 전체의 생성·patch·삭제 목록을 승인받고 서버 health와
복구본을 확인한다. 서버가 준비되지 않으면 helper를 실행하지 않는다.

1. `${LAB_DATA_DIR}/stalwart/data`를 비어 있는 상태로 생성한다. 이전
   `${DEFAULT_COMMUNICATION_DIR}/stalwart/data`의 데이터는 자동으로 옮겨지지 않으며 이전은 별도 승인이다.
   승인된 기동 전에 정확한 새 경로의 소유권·권한이 선언된 이미지 사용자 요구사항과
   일치하는지 확인한다. 자동 소유권 보정을 가정하거나 기존 경로를 넓게 변경하지 않는다.
2. `python3 scripts/operations/lab.py up stalwart --purpose "<목적>" --lease <기간>`으로 lease를
   받아 기동한 다음 `docker compose --env-file labs/.env -f labs/stalwart/docker-compose.yml --profile mail-server run --rm --no-deps stalwart-config`, 그다음
   `docker compose --env-file labs/.env -f labs/stalwart/docker-compose.yml --profile mail-server restart stalwart`를 실행한다.
3. admin UI나 추가 plan을 통해 계정을 생성한다. 합성 메일을 사용하고 본문이나
   credential을 증거에 절대 기록하지 않는다.
4. 외부 배달에는 새로 승인된 요구 사항(DNS, SPF, DKIM, DMARC, 평판)과 릴레이
   규칙에 대한 검토된 변경이 필요하다.

###### 전송 결과 판정
<!-- core-payload-level:4 -->

제출에 대한 SMTP `250` 응답은 Stalwart가 메시지를 queue에 받았다(accepted)는 뜻일 뿐,
수신자에게 배달됐다(delivered)는 뜻이 아니다. 결과는 수신자별로 네 가지로 나눈다.

| 상태 | 근거 | 다음 행동 |
| --- | --- | --- |
| accepted | 제출 `250`, queue에 남아 있음 | 배달 시도를 기다린다 |
| delivered | 원격 서버가 그 수신자에 `250`을 응답했고 queue에서 빠짐 | 완료로 기록한다 |
| failed | 영구 `5xx` 또는 반송(DSN) | 발신 기능에 실패를 알린다 |
| unknown | 본문 전송 뒤 응답 전에 연결이나 Stalwart가 끊김 | 재전송하면 중복될 수 있다 |

unknown은 실패로 단정하지 않는다. 같은 `Message-ID`로 queue와 배달 로그를 먼저
확인하고, 재전송은 수신 측이 같은 `Message-ID`를 중복으로 처리할 수 있을 때만 한다.
앱은 발신 요청마다 고정 `Message-ID`를 정해 재시도에 재사용한다. Mailpit은 개발용
수집 장치이므로 Mailpit에 메일이 보인 것은 외부 배달의 증거가 아니다.

###### Listener 변경과 관리자 회전
<!-- core-payload-level:4 -->

저장소 루트에서 서버의 준비 상태, 적용할 plan 해시, 삭제될 listener 목록, 이전
plan과 datastore 복구본, 중단 영향 및 승인을 확인한다. `stalwart-config`는 서버
health를 기다리는 일회성 변경 작업이며 자체 HTTP health는 없다. 승인된 적용은
`docker compose --env-file labs/.env -f labs/stalwart/docker-compose.yml --profile mail-server run --rm --no-deps stalwart-config`로
정확히 선택한다. 오류가 나면 재시도·재시작을 멈추고 부분 적용 범위를 확인한다.
성공 후 승인된 서버 재시작과 listener·인증·relay 검증을 거친다. 이전 plan 재적용도
삭제·patch를 일으키므로 자동 롤백으로 취급하지 않는다.

관리자 secret 교체는 [공통 수명주기 정책](../../02.policies/01.common/0006-infrastructure-optimization-governance.md)을
따라 단일 파일 bind의 재생성 필요성을 확인한다. 승인된 `stalwart` 재생성 후 새
관리자 인증 성공과 이전 인증 거부를 값 노출 없이 확인한다. helper는 다음 승인된
실행 때 새 secret을 사용한다. 기존 이미지 복원은 datastore 변경을 되돌리지 않는다.

##### Stop Conditions

open-relay 동작, 알 수 없는 backend, backup/key custody 누락, test 중 실제 mail,
DNS/reputation 문제, 비호환 schema/license 동작이 있으면 중단한다.

#### Verification

##### Expected Results

###### Service Checks
<!-- core-payload-level:4 -->

외부 전달 전에 relay denial(SMTP `550`과 `Relay not allowed`)과 승인된 synthetic submission/retrieval 하나가 확인되어야 하고, listener·인증·relay 검증이 성공해야 한다.

###### Evidence
<!-- core-payload-level:4 -->

종료 코드·listener/TLS/DNS 판정·backend 종류·백업 ID/checksum·개수·합성 test ID·
release/source 커밋과 최종 상태만 기록한다.

##### Unverified Conditions

이 runbook이 아직 관찰하지 못한 항목은 다음과 같다. 문서는 대부분의 변경 단계에 승인을 요구한다.

- bounded state 캡처와 relay denial 확인: 이 문서에는 실행 결과가 기록되어 있지 않다. SMTP `550`과 `Relay not allowed`, 합성 submission/retrieval이 관찰되면 검증된다.
- backup과 isolated restore: 실행 결과가 기록되어 있지 않다. 복원 후 설정/계정/mailbox 개수, 합성 IMAP 조회, queue 상태가 관찰되면 검증된다.
- upgrade: 복원 data에서 target image를 테스트한 결과가 기록되어 있지 않다.
- 승인된 최초 기동과 listener 변경(`stalwart-config`): 승인이 필요하며 실행 결과가 기록되어 있지 않다. 적용 후 listener/인증/relay 검증이 관찰되면 검증된다.
- 관리자 secret 회전: 새 인증 성공과 이전 인증 거부가 관찰되기 전에는 검증되지 않았다.
- 외부 배달: DNS, SPF, DKIM, DMARC, 평판 요구 사항 승인이 필요하며 기록이 없다. 수신자 `250` 응답과 queue 제거가 관찰되면 delivered로 검증된다.
