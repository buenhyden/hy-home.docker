# Data Tier (04-data) Product Requirements

## Overview

### Overview

### Problem and Goals

This document defines the product requirements for the `04-data` tier. As the unified data layer that stores and manages all state for the `hy-home.docker` platform, it clarifies user value, problem definition, and success criteria to serve as the basis for subsequent design and implementation.

### Problem Statement

Modern home server environments require diverse data cycles, including relational (SQL), cache (KV), unstructured (object), and AI search (vector). Managing these individually increases operational complexity and fragments authorization and backup policy.

## Requirements

### Requirements

### Functional Requirements

- **REQ-0004-FR-0001**: HOME and DEV databases (`mng-pg`, `mng-valkey`, `dev-pg`, `dev-valkey`) run as single nodes and are not highly available; their recovery path is backup and restore. PostgreSQL and Valkey replication and failover are exercised only in the standalone LABs (`labs/postgresql-ha.yml`, `labs/valkey-cluster.yml`), whose nodes share one host and therefore are not host HA (SPEC-0215).
- **REQ-0004-FR-0002**: Data traffic must be isolated to a declared internal network, blocking external access.
- **REQ-0004-FR-0003**: Passwords and sensitive information must be injected via Docker Secrets or OpenBao.
- **REQ-0004-FR-0004**: All data must be persisted under `${DEFAULT_DATA_DIR}`.

### Non-functional Requirements

No separately numbered non-functional requirement was identified in the source package.

### Interface Requirements

No separately numbered solution-independent external interface requirement was identified in the source package.

## Acceptance Criteria

- **REQ-0004-FR-0001**: No document calls a single-node HOME or DEV database HA. A LAB failover exercise records its observed failover time; a 30 second target applies only to that exercise.
- **REQ-0004-FR-0002**: Metrics for all data services must be collected 100% through Prometheus.
- **REQ-0004-FR-0003**: Data integrity must be guaranteed at 99.99% during recovery from a backup copy.

## Scope

### Scope

### Stakeholders and User Needs

Provide a resilient data hub through which applications can persist data via a consistent interface, regardless of the physical placement or failure state of the data store.

### Personas

- **Backend Developers**: Service developers who need reliable data APIs (SQL, Redis, S3).
- **Data Engineers**: Engineers who build data pipelines and analytics environments.
- **AI Agents**: Agents that need a vector engine for knowledge-base (RAG) search.

### Key Use Cases

- **STORY-01**: A user must be able to safely store and query business data in PostgreSQL that is recoverable from backup.
- **STORY-02**: A developer must be able to process session and temporary data in milliseconds via a Valkey cache.
- **STORY-03**: The system must reliably store large media and log data in S3-compatible object storage (SeaweedFS).
- **STORY-04**: An AI service must search high-dimensional vector embeddings (Qdrant) to generate intelligent responses.

### Constraints

- **In Scope**: Deployment configuration, backup and restore, network isolation, and secret management for data services; replication and failover only as standalone LAB exercises.
- **Out of Scope**: Business logic internal to individual applications, development of data migration tools.
- **Non-goals**: Embedding a real-time data visualization dashboard (owned by the Observability tier).

### AI Agent Requirements

N/A

### Risks

- **Risks**: Single-node HOME and DEV databases have no failover, so recovery depends on backups; multi-node LABs add RAM/CPU load on the same host.
- **Dependencies**: Stability of Docker Compose and the container runtime, available space in `${DEFAULT_DATA_DIR}`.
- **Assumptions**: Services are assumed to communicate only within a shared network.
